# Дорожная карта проекта

Единственный источник правды о том, что сделано, что делается и почему приняты
те или иные решения. Вкладки Claude Code не синхронизируются между собой —
общее у них только содержимое репозитория, поэтому актуальное состояние живёт
здесь, а не в истории переписки.

**Файл обязателен к обновлению.** Окно, закрывшее задачу, дописывает сюда
результат до того, как задача считается завершённой.

---

## Как продолжать работу

1. Задачи берутся по одной, в порядке приоритета из списка ниже.
2. Под задачу заводится ветка от `dev`: `git checkout -b <тип>/<имя> dev`.
3. Задача решается в отдельной вкладке. Ввод в курс дела — одной фразой:
   «прочитай `docs/ROADMAP.md`, берём задачу N».
   Мелкие задачи (десять минут, пара команд) выгоднее добивать в текущей
   вкладке: новое окно потратит больше времени на разведку, чем сама задача.
4. Обсуждение предшествует изменениям. Код и конфигурация правятся после
   явного согласия.
5. Коммиты и описания pull request — подробные, по-русски: что сделано,
   зачем и что это меняет.
6. По завершении задача дописывает в этот файл: что сделано, какие решения
   приняты по ходу, что осталось незакрытым.

Несколько вкладок делят одну рабочую копию и одну текущую ветку, поэтому
задачи идут последовательно. Для параллельной работы нужен отдельный
git worktree.

## Задача 0 — битый `STRIPE_SECRET_KEY` в продакшене

**Статус:** обнаружено 7 сентября 2026 при проверке задачи 1. Блокирует всё
остальное в платёжном флоу. Не начата.

**Что произошло.** Значение `STRIPE_SECRET_KEY` в окружении Production — это
буквально строка `sk_test_` длиной восемь символов, то есть обрезанная при
вставке. Stripe отвечает на неё `StripeAuthenticationError: Invalid API Key
provided: sk_test_`.

**Как это доказано, а не предположено.** Прод нельзя расспросить напрямую:
Vercel не отдаёт значения Secret-переменных, `vercel env pull` возвращает
`[SENSITIVE]`. Поэтому диагноз собран из двух наблюдений. Первое: в
боевых логах ошибка воспроизводится на двух независимых путях кода —
`[CANCEL_API]` из `src/app/api/checkout/cancel/route.ts` и
`[CHECKOUT_SUCCESS]` из `src/lib/checkout-outcome.ts`, оба через
`stripe.checkout.sessions.retrieve`. Второе: Stripe маскирует ключ в этом
сообщении по понятному правилу — ключ до двенадцати символов возвращается
как есть, длиннее заменяется звёздочками с сохранением последних четырёх
(проверено тремя заведомо неверными ключами). Прод отдаёт `sk_test_` без
единой звёздочки, а значит настоящее значение и есть эти восемь символов.

**Чем это грозит прямо сейчас.** Продакшен вообще не может разговаривать с
API Stripe. Оформление заказа падает на `stripe.checkout.sessions.create`;
по ветке в `src/actions/checkout.ts` это не сетевая ошибка, поэтому бронь
откатывается, заказ уходит в `CANCELLED`, а покупатель видит «Ошибка связи с
платежной системой. Попробуйте еще раз». Данные при этом не портятся — откат
отрабатывает штатно, — но купить в магазине нельзя ничего. Судя по метке
создания переменной, так продолжается около суток.

**Чем чинится.** Ключ из локального `.env` проверен и валиден: 107 символов,
тестовый режим, аккаунт `acct_1TnJtKL9uPyB4436`, успешно достаёт сессию через
API. Его достаточно переложить в Vercel, не печатая значение в терминал:

```
vercel env rm STRIPE_SECRET_KEY production
grep -E '^STRIPE_SECRET_KEY=' .env | cut -d= -f2- | tr -d '"' \
  | vercel env add STRIPE_SECRET_KEY production --sensitive
```

После этого обязателен редеплой — переменные подхватываются только новой
сборкой.

## Задача 1 — вебхук Stripe в продакшене

**Статус:** сделано наполовину, упирается в задачу 0 и в право на редеплой.
Ветка `feat/stripe-production-webhook`, коммит `fe197c8`.

**Проблема (исходная).** `STRIPE_WEBHOOK_SECRET` отсутствовал на Vercel, а
`src/app/api/webhooks/stripe/route.ts` читает его на уровне модуля и передаёт
в `constructEventAsync`. Даже если создать эндпоинт в дашборде Stripe, каждое
событие упадёт на верификации подписи и вернёт 400. Локальный секрет из
`stripe listen` для продакшена не подойдёт — у постоянного эндпоинта свой.

**Чем это грозит.** Сейчас единственный путь проведения заказа — страница
успеха (`resolveOutcome` вызывает `fulfillOrder`). Заказ проводится, только
если покупатель дождался редиректа из Stripe обратно. Если он закрыл вкладку
сразу после оплаты, заказ остаётся `PENDING`; через 40 минут
(`DB_RESERVATION_MINUTES` в `src/actions/checkout.ts`) он попадает под снятие
брони. Итог: деньги списаны, вещь снова в продаже, заказа нет. Вебхук
задумывался именно как страховка от этого и не работает.

**Сделано.**

1. Эндпоинт заведён через Stripe CLI: `we_1UCydkL9uPyB44368SAnNf3h`,
   `https://art-jane.vercel.app/api/webhooks/stripe`, статус `enabled`,
   тестовый режим. Подписан на четыре события: `checkout.session.completed`,
   `checkout.session.async_payment_succeeded`,
   `checkout.session.async_payment_failed`, `checkout.session.expired`.
   Постоянного эндпоинта до этого не существовало вовсе — не только секрета
   не было, но и адресата, так что Stripe никуда ничего не слал.
   `api_version` эндпоинта прибит к `2026-06-24.dahlia`, той же, что
   `STRIPE_API_VERSION` в `src/lib/stripe.ts`: иначе смена версии по умолчанию
   у аккаунта тихо разошлась бы с типами SDK.
2. Секрет добавлен в Vercel как Secret для Production.
3. Код: в `src/app/api/webhooks/stripe/route.ts` секрет читается внутри
   обработчика, без non-null assertion, отсутствие даёт 500 и отдельный лог.
   Комментарий в `src/app/api/cron/release-reservations/route.ts` приведён
   к реальному суточному расписанию.

**Осталось.**

1. Починить задачу 0 — без валидного `STRIPE_SECRET_KEY` продакшен не может
   создать ни одной сессии, и проверять вебхуку будет нечего.
2. Редеплой продакшена. Заблокирован: агент не имеет права запускать
   `vercel redeploy --target production`, нужно правило в настройках
   Claude Code либо запуск руками.
3. Проверка доставки по плану из журнала ниже.

**Замер «до», сделанный 7 сентября.** После создания эндпоинта `stripe trigger
checkout.session.completed` дошёл до прода и получил `400`, в логах —
`[STRIPE_WEBHOOK] Ошибка верификации подписи: TypeError ... Received undefined`.
Stripe ретраил трижды. Это подтверждает сразу три вещи: доставка от Stripe до
приложения работает, причина отказа — именно пустой секрет, и старый код
действительно маскировал конфигурационную ошибку под подделку подписи.

## Задача 5 — cron и ручная проверка платежей

**Статус:** не начата. Отдельная вкладка.

Расписание в `vercel.json` — `0 3 * * *`, суточное, из-за ограничений тарифа
Hobby. При TTL брони в 40 минут брошенная бронь держит уникальную вещь до
суток. Роут спроектирован так, что его может дёргать любой внешний
планировщик с заголовком `Authorization: Bearer $CRON_SECRET`, поэтому
расписание в GitHub Actions решает задачу бесплатно. Альтернативы —
Supabase `pg_cron` или тариф Vercel Pro.

Сценарии, которые не проверяются кодом и остались непройденными:

- реальный платёж тестовой картой от корзины до `PaidView`;
- две вкладки одновременно на одном аккаунте — ожидается `PROCESSING_ERROR`,
  а не отмена первого заказа;
- открытие чужого `session_id` под другим пользователем — ожидается
  `UnconfirmedView` без мутации заказа.

## Журнал выполнения

Сюда каждое окно дописывает результат закрытой задачи.

- **7 сентября 2026.** Сведены `main` и `dev` на `12e260e`. Проведён аудит
  окружения Vercel, составлен этот план, зафиксирован порядок работы.
- **7 сентября 2026, задача 1.** Заведён вебхук-эндпоинт в Stripe, секрет
  положен в Vercel, код поправлен (`fe197c8`). При проверке обнаружена
  задача 0 — битый `STRIPE_SECRET_KEY` в проде. Задача 1 не закрыта:
  ждёт починки ключа и редеплоя.

    **План проверки, когда ключ починят и редеплой пройдёт.** Порядок важен,
    каждый шаг доказывает ровно одну вещь.

    1. _Подпись сходится._ `stripe trigger checkout.session.completed`, затем
       в логах Vercel ждём `200` и строку «В metadata сессии … нет orderId» —
       сессию создал триггер, `orderId` в ней и не должно быть. База не
       затрагивается.
    2. _Снятие брони без оплаты — самый чистый тест._ Оформить заказ на проде
       до страницы Stripe Checkout, скопировать `cs_test_…` из адреса (кусок
       между `/pay/` и решёткой), закрыть вкладку **не нажимая «назад»** —
       кнопка «назад» ведёт на cancel-роут и отменит заказ сама. Затем
       `stripe checkout sessions expire cs_test_…`. Ожидается: заказ
       `CANCELLED`, товар `AVAILABLE`, `reservedUntil` пуст. В этот момент не
       открыта ни одна страница приложения и cron спит, поэтому сработать мог
       только вебхук — пройти этот тест случайно невозможно.
    3. _Оплата, когда покупатель не дошёл до страницы успеха._ Дойти до Stripe
       Checkout, во второй вкладке **выйти из аккаунта**, оплатить картой
       `4242 4242 4242 4242`. Страница успеха проверяет владельца до мутации,
       поэтому разлогиненному посетителю она покажет «не удалось подтвердить»
       и ничего не изменит — провести заказ сможет только вебхук. Ожидается:
       заказ `PAID`, товар `SOLD`, позиции удалены из корзины в базе, в логах
       нет `[ALARM_ORPHAN_PAYMENT]`. Это надёжнее, чем гонка за скоростью
       закрытия вкладки.
    4. _Чего проверить нельзя._ В `src/actions/checkout.ts` задано
       `payment_method_types: ['card']`, поэтому события
       `checkout.session.async_payment_succeeded` и `async_payment_failed`
       в проде не выстрелят никогда. Они подписаны на будущее, когда появятся
       SEPA или Klarna; их молчание не признак поломки.

    **Ловушки, выясненные по ходу.** Все тестовые заказы ложатся в боевую базу
    Supabase — она одна на все окружения (задача 4), так что идентификаторы
    тестовых заказов надо выписывать и потом убирать. Пока запущен
    `stripe listen`, он получает все события тестового режима аккаунта,
    включая порождённые продом, и при общей базе локальный обработчик начнёт
    менять те же самые заказы: во время прод-проверок его надо держать
    выключенным. Локальному приложению нужен свой `whsec_…` из вывода
    `stripe listen`, с продовым он не связан.
