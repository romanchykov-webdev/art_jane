# Дорожная карта проекта

Единственный источник правды о том, что сделано, что делается и почему приняты
те или иные решения. Вкладки Claude Code не синхронизируются между собой —
общее у них только содержимое репозитория, поэтому актуальное состояние живёт
здесь, а не в истории переписки.

**Файл обязателен к обновлению.** Окно, закрывшее задачу, дописывает сюда
результат до того, как задача считается завершённой.

---

## Как продолжать работу

1. Задачи берутся по одной, в порядке приоритета из списка ниже.
2. Под задачу заводится ветка от `dev`: `git checkout -b <тип>/<имя> dev`.
3. Задача решается в отдельной вкладке. Ввод в курс дела — одной фразой:
   «прочитай `docs/ROADMAP.md`, берём задачу N».
   Мелкие задачи (десять минут, пара команд) выгоднее добивать в текущей
   вкладке: новое окно потратит больше времени на разведку, чем сама задача.
4. Обсуждение предшествует изменениям. Код и конфигурация правятся после
   явного согласия.
5. Коммиты и описания pull request — подробные, по-русски: что сделано,
   зачем и что это меняет.
6. По завершении задача дописывает в этот файл: что сделано, какие решения
   приняты по ходу, что осталось незакрытым.

Несколько вкладок делят одну рабочую копию и одну текущую ветку, поэтому
задачи идут последовательно. Для параллельной работы нужен отдельный
git worktree.

## Задача 0 — битый `STRIPE_SECRET_KEY` в продакшене

**Статус:** закрыта 7 сентября 2026. Ключ перезаписан валидным значением из
локального `.env` командой `vercel env add … --sensitive --force` (ответ CLI —
«Overrode»), продакшен передеплоен. После этого `[CANCEL_API]` и
`[CHECKOUT_SUCCESS]` перестали писать ошибку, а приложение снова создаёт
сессии Stripe — проверено настоящим оформлением заказа.

**Что произошло.** Значение `STRIPE_SECRET_KEY` в окружении Production — это
буквально строка `sk_test_` длиной восемь символов, то есть обрезанная при
вставке. Stripe отвечает на неё `StripeAuthenticationError: Invalid API Key
provided: sk_test_`.

**Как это доказано, а не предположено.** Прод нельзя расспросить напрямую:
Vercel не отдаёт значения Secret-переменных, `vercel env pull` возвращает
`[SENSITIVE]`. Поэтому диагноз собран из двух наблюдений. Первое: в
боевых логах ошибка воспроизводится на двух независимых путях кода —
`[CANCEL_API]` из `src/app/api/checkout/cancel/route.ts` и
`[CHECKOUT_SUCCESS]` из `src/lib/checkout-outcome.ts`, оба через
`stripe.checkout.sessions.retrieve`. Второе: Stripe маскирует ключ в этом
сообщении по понятному правилу — ключ до двенадцати символов возвращается
как есть, длиннее заменяется звёздочками с сохранением последних четырёх
(проверено тремя заведомо неверными ключами). Прод отдаёт `sk_test_` без
единой звёздочки, а значит настоящее значение и есть эти восемь символов.

**Чем это грозит прямо сейчас.** Продакшен вообще не может разговаривать с
API Stripe. Оформление заказа падает на `stripe.checkout.sessions.create`;
по ветке в `src/actions/checkout.ts` это не сетевая ошибка, поэтому бронь
откатывается, заказ уходит в `CANCELLED`, а покупатель видит «Ошибка связи с
платежной системой. Попробуйте еще раз». Данные при этом не портятся — откат
отрабатывает штатно, — но купить в магазине нельзя ничего. Судя по метке
создания переменной, так продолжается около суток.

**Чем чинится.** Ключ из локального `.env` проверен и валиден: 107 символов,
тестовый режим, аккаунт `acct_1TnJtKL9uPyB4436`, успешно достаёт сессию через
API. Его достаточно переложить в Vercel, не печатая значение в терминал:

```
vercel env rm STRIPE_SECRET_KEY production
grep -E '^STRIPE_SECRET_KEY=' .env | cut -d= -f2- | tr -d '"' \
  | vercel env add STRIPE_SECRET_KEY production --sensitive
```

После этого обязателен редеплой — переменные подхватываются только новой
сборкой.

## Задача 1 — вебхук Stripe в продакшене

**Статус:** закрыта 7 сентября 2026. Вебхук работает в продакшене, проверен

**Проблема (исходная).** `STRIPE_WEBHOOK_SECRET` отсутствовал на Vercel, а

**Сделано.**

1. Эндпоинт заведён через Stripe CLI: `we_1UCydkL9uPyB44368SAnNf3h`,
   `https://art-jane.vercel.app/api/webhooks/stripe`, статус `enabled`,

   не было, но и адресата, так что Stripe никуда ничего не слал.

2. Секрет добавлен в Vercel как Secret для Production.
3. Код: в `src/app/api/webhooks/stripe/route.ts` секрет читается внутри
   обработчика, без non-null assertion, отсутствие даёт 500 и отдельный лог.
   Комментарий в `src/app/api/cron/release-reservations/route.ts` приведён
   к реальному суточному расписанию.

**Как проверено.** Замер «до»: сразу после создания эндпоинта `stripe trigger`
дошёл до прода и получил `400` с `Received undefined` в логах, Stripe ретраил
трижды — доставка работает, причина отказа именно пустой секрет, а старый код

«после» и два сквозных сценария описаны в журнале.

## Задача 3 — гигиена окружения

**Статус:** закрыта 8 сентября 2026. Ветка `chore/env-hygiene`.

**Сделано с переменными на Vercel.**

- `STRIPE_SECRET_KEY` добавлен в Preview. Раньше preview-сборки падали на
  `Neither apiKey nor config.authenticator provided` при вычислении модуля
  `src/lib/stripe.ts`, из-за чего проверки в pull request были бесполезны.
  Значение переложено конвейером `grep … | vercel env add --sensitive`, без
  ручной вставки: именно ручная вставка обрезала ключ до восьми символов в
  задаче 0.
- `NEXT_PUBLIC_BETTER_AUTH_URL` удалена.
- `BETTER_AUTH_URL` оставлена как есть и теперь работает запасным значением.

**Важная поправка к прежней записи.** Здесь раньше стояло, что
`NEXT_PUBLIC_BETTER_AUTH_URL` — «мёртвая переменная». Это неверно: её читает
сама библиотека. В `better-auth/dist/utils/url.mjs` порядок такой —
`BETTER_AUTH_URL`, затем `NEXT_PUBLIC_BETTER_AUTH_URL`, затем ещё несколько
имён. Переменная не встречалась в `src/` и потому выглядела неиспользуемой,
но фактически она с высоким приоритетом задавала адрес и на клиенте тоже.
Удалять её было нужно — но не как мусор, а как обязательное условие того,
чтобы клиент перестал быть прибит к одному домену.

**Сделано в коде.**

`src/lib/auth.ts` перешёл на динамический `baseURL`, который better-auth 1.6.2
поддерживает штатно (тип `DynamicBaseURLConfig`):

```ts
baseURL: {
    allowedHosts, protocol, fallback;
}
```

Список хостов собирается из системных переменных Vercel —
`VERCEL_PROJECT_PRODUCTION_URL`, `VERCEL_URL`, `VERCEL_BRANCH_URL` — плюс
`localhost:3000`. Адрес вычисляется на каждый запрос из его же заголовка
`x-forwarded-host`, поэтому один и тот же код работает и на проде, и на любом
превью-деплое, и локально. `trustedOrigins` better-auth выводит из
`allowedHosts` сам.

Подстановочный шаблон `*.vercel.app` сознательно **не** используется: хост
приходит из запроса, и такой шаблон разрешил бы подставить любой чужой домен
на `vercel.app`, а вместе с ним и адрес OAuth-редиректа.

`protocol` задан явно (`https` на Vercel, `http` локально), а не оставлен на
`auto`. Причина тонкая: имя cookie выбирается один раз при инициализации, и
при динамическом `baseURL` без явного протокола better-auth решал бы про
префикс `__Secure-` по `NODE_ENV`. Локальная сборка `next build && next start`
тоже идёт с `NODE_ENV=production`, из-за чего cookie на localhost разошлись бы
с поведением под `next dev`. С явным протоколом имя cookie совпадает с прежним
в обоих окружениях, и уже выданные сессии остались в силе.

`fallback` берётся из `BETTER_AUTH_URL`. Если системные переменные почему-то
не придут, поведение деградирует до прежнего фиксированного адреса, а не до
отказа в авторизации.

`src/lib/auth-client.ts` больше не задаёт `baseURL` вовсе. Раньше там стоял
`NEXT_PUBLIC_APP_URL`, который вшивается в бандл на сборке и на превью
указывал на продакшен: браузер отправлял запросы авторизации на чужой домен,
и cookie ставились не туда, где их потом ищут. Без `baseURL` better-auth в
браузере берёт `window.location.origin`, а при серверном рендере —
`VERCEL_URL` текущего деплоя.

**Как проверено.** Приложение собрано и запущено локально дважды: обычным
образом и с переменными, имитирующими превью-деплой Vercel. Для каждого хоста
инициировался вход через Google, и проверялось, какой `redirect_uri` уходит в
запросе к Google:

| Заголовок `x-forwarded-host`      | Полученный `redirect_uri`          |
| --------------------------------- | ---------------------------------- |
| `art-jane.vercel.app`             | свой домен                         |
| домен деплоя (`VERCEL_URL`)       | свой домен                         |
| домен ветки (`VERCEL_BRANCH_URL`) | свой домен                         |
| `localhost:3000`                  | свой домен                         |
| `evil.vercel.app`                 | запасной адрес, не хост из запроса |
| `attacker.example.com`            | запасной адрес, не хост из запроса |

То есть подмена заголовка `x-forwarded-host` не уводит OAuth-редирект на чужой
домен. Отдельно отмечено: у better-auth включён рейт-лимит, и при частых
подряд запросах эндпоинт отвечает `429` — первый прогон этой проверки дал
ложное «не работает» именно из-за него, между запросами нужны паузы.

`npm run check` (типы, линт, формат, `prisma validate`), 33 юнит-теста и
`npm run build` проходят чисто.

**Тесты.** Сборка списка хостов вынесена в `src/lib/auth-hosts.ts` отдельным
модулем — импорт `auth.ts` тянет Prisma и инициализацию better-auth, поэтому
проверить одну лишь логику списка через него нельзя. Восемь тестов в
`src/lib/auth-hosts.test.ts`; главный из них запрещает подстановочные шаблоны,
и сам модуль их отбрасывает с предупреждением в лог. Остальное поведение —
библиотечное и проверено на запущенной сборке.

**Про превью-домены.** Вход через Google на них не заработает: Google требует
заранее зарегистрированный `redirect_uri`, а домен превью меняется от сборки
к сборке. Решено оставить так — см. задачу 8. Вход по паролю на превью
работает.

## Задача 4 — разделить базы разработки и продакшена

**Статус:** отложена до запуска 9 сентября 2026. Не отменена — входит в
чек-лист запуска (см. ниже). Сейчас за неё браться не нужно.

**Почему отложена.** Магазин ещё не работает по-настоящему: настоящих
покупателей, настоящих денег и настоящих заказов нет, а всё содержимое базы —
разработочное. Значит ущерба, от которого защищает разделение, сегодня не
существует, и с базой можно делать что угодно. Прежняя формулировка называла
общую базу главным архитектурным риском — это было верно по механике, но
неверно по стадии проекта.

**Побочная польза отсрочки.** Пока данные не настоящие, проверки платёжного
флоу можно проводить свободно: сломал, посмотрел, пересоздал. Уборка после
тестовых заказов, которую приходилось делать в задаче 1, больше не нужна.

**Что именно останется сделать.** Завести отдельный проект Supabase для
разработки, сделать `DATABASE_URL`/`DIRECT_URL` пер-окруженческими, перевести
локальный `.env` на базу разработки.

**Почему это обязательно перед запуском.** Одна база на все окружения уже
однажды превратила обычное отставание деплоя в аварию авторизации. С момента
появления настоящих заказов любой локальный `prisma db push`, наполнение
тестовыми данными или прогон тестов будет писать в боевые данные. Починку
истории миграций уже приходилось делать на живой базе с 19 заказами — с
настоящими заказами так рисковать нельзя.

**Внешний планировщик решено не заводить.** Освобождение брони держится не на
cron, а на вебхуке: в `src/actions/checkout.ts` `STRIPE_SESSION_MINUTES = 32`
против `DB_RESERVATION_MINUTES = 40`, а `checkout.session.expired` обработан
в вебхуке и вызывает `releaseOrder`. Брошенная бронь снимается примерно за
полчаса, а не за сутки; суточный прогон — страховка на случай недоставленного
вебхука, которую Stripe вдобавок дублирует собственными ретраями. Расписание
в GitHub Actions добавило бы копию секрета в ещё одно хранилище и само по себе
опаздывает на десять-двадцать минут под нагрузкой, `pg_cron` требует `pg_net`
и HTTP-вызовов из базы, тариф Pro — денег за тот же результат. Если однажды
захочется сузить окно расхождения, дешевле не планировщик, а сближение
`DB_RESERVATION_MINUTES` с 32 минутами.

**Прежнее доказательство «cron не отработал ни разу» опровергнуто.** Заказ
`6fc7316b-500f-4bc8-8603-ed3ec260993c` (создан 1 августа, `expiresAt`
1 августа 14:36 UTC) имеет `updatedAt` = **8 сентября 03:44:27 UTC** и статус
`CANCELLED`, три его товара снова `AVAILABLE`. Это попадание в часовое окно
расписания; ручных вызовов в журнале нет, cancel-роут не дёргался, страницы
никто не открывал — сработать могло только расписание. Активным тогда был
прод-деплой от 7 сентября, первый с валидным `vercel.json`.

Пять недель простоя объясняются двумя независимыми причинами, и обе были
устранены ещё до взятия задачи. Первая: исходное расписание `*/10 * * * *`
Hobby отклоняет, из-за чего падал весь деплой — починено `12e260e`
6 сентября. Вторая: вебхук-эндпоинт в продакшене появился только 7 сентября
в рамках задачи 1, а до этого заказ не мог освободиться вообще ничем.

**Ловушка: локальный `CRON_SECRET` не совпадает с продовым.** Значение
в `.env` — корректный 64-символьный hex без кавычек и лишних символов, и всё
равно даёт 401. На Vercel переменная заведена с типом **Secret**, поэтому
`vercel env pull --environment=production` пишет вместо неё `[SENSITIVE]`,
а дашборд значения не показывает. На работу расписания это не влияет —
заголовок формирует сам Vercel из своей копии. Мешает единственному: дёрнуть
роут снаружи руками. Обходится штатной командой

```
vercel crons run /api/cron/release-reservations
```

— Vercel триггерит джобу сам и подставляет правильный секрет. Синхронизировать
секреты понадобится только при появлении внешнего планировщика, и это будет
перезапись переменной **вместе с редеплоем**: функция читает окружение,
зафиксированное на момент сборки, поэтому смена значения без редеплоя временно
сломает ночной прогон.

### Проверка платёжного флоу — пройдена 9 сентября 2026

Два сценария, которые нельзя доказать кодом, пройдены на продакшен-сборке,
поднятой локально. Настоящая оплата ни для одного из них не требовалась: оба
отрабатывают до платежа, поэтому `stripe listen` не запускался и прод не
трогался.

**Сценарий А — две вкладки на одном аккаунте.** Гонка сделана детерминированной:
вместо попыток попасть в полуторасекундное окно, пока Stripe отвечает, в
`CheckoutLock` вручную вставлялась строка с будущим `expiresAt`.

| Шаг                              | Результат                                                                      |
| -------------------------------- | ------------------------------------------------------------------------------ |
| Лок занят → «Proceed to Payment» | Модалка «Заказ обрабатывается — Ваш заказ формируется»                         |
| Какая ветка сработала            | `src/actions/checkout.ts:117`, ветка лока — не вторая, с текстом «уже оплачен» |
| Побочные эффекты                 | Заказов у пользователя `0`; товар `AVAILABLE`, `reservedUntil = null`          |
| Лок снят → повторное нажатие     | Редирект на Stripe, сессия создана                                             |

Последняя строка обязательна: без неё нельзя отличить «сработал лок» от
«сломалось что-то другое». Попутно подтвердилось, что блок `finally`
отрабатывает — после успешного оформления локов в базе `0`.

**Сценарий Б — чужой `session_id`.** Пользователь B открыл ссылку успеха
пользователя A и получил `UnconfirmedView` («НЕ УДАЛОСЬ ПОДТВЕРДИТЬ ЗАКАЗ»).
Заказ A после этого: статус `PENDING`, `updatedAt` не изменился, товар
`RESERVED` с тем же `reservedUntil`, записей `[ALARM_*]` в логах нет.

**Контрольная проверка — без неё первые две ничего не стоят.** Владелец A вошёл
обратно и открыл **тот же адрес**: получил `ProcessingView` («ПЛАТЁЖ
ОБРАБАТЫВАЕТСЯ»), а не отказ. Без этого шага поведение «отказываем всем подряд»
выглядело бы неотличимо от работающей проверки владельца.

**Уборка.** Сессия Stripe погашена явно — иначе через ~32 минуты она прислала
бы `checkout.session.expired` на **боевой** вебхук уже удалённого заказа.
Дальше удалены заказ, строки корзины и два тестовых пользователя, товар
возвращён в `AVAILABLE`. База совпала с исходной цифра в цифру: заказы
`CANCELLED=18, PAID=2`, товары `SOLD=2, AVAILABLE=39`, 5 пользователей, 0 локов,
7 строк в корзинах.

**Что из этого следует.** Платёжный контур проверен целиком: настоящая оплата
(7 сентября, задача 1), снятие брони по истечении сессии через вебхук (там же),
сериализация параллельных оформлений и защита чужого заказа (9 сентября).
Модуль продаж можно считать подтверждённым и показывать тестировщикам.

## Задача 6 — неуникальные вещи: решение и фундамент на будущее

**Статус:** решено 9 сентября 2026 **ничего не менять**. Раздел оставлен не как
невыполненная работа, а как готовый разбор на тот случай, если владелец
однажды захочет продавать неуникальные вещи. Начинать тогда следует отсюда,
а не с чистого листа.

### Решение

Модель остаётся прежней: **одна строка `Product` = одна физическая вещь.**
Складских остатков, вариантов и количеств не вводим.

### Почему именно так

Обсуждался конкретный сценарий: белая футболка в размерах S, M, XL, и,
возможно, с печатью. Выяснилось, что **текущая модель его уже выражает**.
`Product` — это единица товара, а не модель товара: `status` и `reservedUntil`
лежат прямо на строке, и `size` у неё уже есть. Десять футболок в трёх
размерах — это десять строк `Product`. Бронирование, `FOR UPDATE`, оплата и
вебхук работают без единой правки. Не хватает только **представления**:
каталог покажет десять почти одинаковых карточек вместо одной с выбором
размера.

Ожидание почти ничего не стоит. Переход к вариантам аддитивен: добавляется
таблица, каждому товару создаётся один вариант, `CartItem` и `OrderItem`
перенаправляются — миграция данных механическая. А дорогая половина,
переписывание платёжного контура, **стоит одинаково сегодня и через год**.
Значит «сделаем заранее, чтобы потом не мучиться» здесь не работает: мучение
переносится на сегодня, и вдобавок мы месяцами тащим неиспользуемую сложность
под требование, форма которого ещё неизвестна.

### Чем опасен складской счётчик — главное, что нельзя забыть

Замена состояния строки на счёток `stock`/`reserved` выглядит как одно поле, а
на деле **теряет идентичность брони**. Сейчас `releaseOrder` в
`src/lib/orders.ts` фильтрует снятие по `status = RESERVED` и
`reservedUntil = order.expiresAt`, то есть умеет спросить «эта бронь всё ещё
моя?». Комментарий там объясняет цену ошибки: иначе вещь в единственном
экземпляре уйдёт двум покупателям сразу. Счётчик `reserved = 3` такого вопроса
задать не может — он не помнит, чьи это три, и уменьшение снимет чужую бронь.
Штатное решение этой проблемы в маркетплейсах — таблица резерваций по строке
на каждую занятую единицу, то есть возврат к тому, что уже есть.

Второе: **количества нет нигде во всей цепочке.** У `CartItem` стоит
`@@unique([productId, userId])` и нет поля `quantity`, у `OrderItem` его тоже
нет. Сейчас это согласованность, а не недоделка. Появление остатков потянет
`quantity` через корзину, строку заказа, подсчёт суммы, позиции Stripe и
логику брони — второй рефакторинг, спрятанный за первым.

### Граница, которую нельзя переходить

Когда работа всё-таки начнётся, действует правило:

> **Представление дублируем, платёж — нет.**

Отдельными можно и нужно делать карточку товара, страницу товара, запросы
каталога и группировку. Едиными обязаны остаться `Order`, `OrderItem`,
создание сессии Stripe, вебхук, бронирование и снятие брони, cron и
`CheckoutLock`.

Причина не в экономии, а в трёх вещах. Смешанная корзина: покупатель захочет
уникальное платье и футболку размера M одним заказом, а два платёжных пути
такой заказ выразить не могут — заказ один, сессия Stripe одна. Повторная
закалка: мьютекс, проверка владельца до мутации, алярмы на осиротевший платёж,
идемпотентность, сборщик зависших броней — всё это второй путь получит заново,
вместе с ненайденными багами, и проверялось оно настоящими платежами вручную,
а не тестами. И вебхук: он один на аккаунт Stripe, получает события обоих
видов, и развилка в самом критичном куске кода удваивает слепые зоны — а мы уже
убедились, что вебхука может не быть месяцами и никто не заметит.

Рекомендуемая форма расширения, не нарушающая границу: `Product` остаётся
единицей товара, сверху добавляется группа (модель товара). «Белая футболка M,
пять штук» — это пять строк `Product` под одной моделью. Карточка и страница
новые, платёжный контур не тронут.

### Вопросы владельцу, без ответов на которые начинать нельзя

1. **Печать: выбирает её покупатель или владелец публикует готовые
   комбинации?** Это две совершенно разные системы. Выбор покупателем — это
   конфигуратор и производство под заказ: бронировать нечего, остаток не
   кончается, зато появляются срок изготовления и, как правило, невозвратность.
   Готовые комбинации — это просто больше товаров, и текущая модель их уже
   поддерживает. Неверная догадка здесь — главный риск всей задачи.
2. **Пять одинаковых футболок размера M — одна строка с остатком 5 или пять
   строк?** Для ручной работы пять строк честнее: каждая вещь физически
   отдельная.
3. **Фотографии общие на модель или свои у каждой единицы?** На `Product`
   висят `thumbnailFront`, `thumbnailBack`, `gallery[]` и последовательность
   360° — `sequenceFolder` со `sequenceFrameCount`, по умолчанию 174 кадра.
   Размеры снимки делят, а принты нет: каждому принту нужны свои фотографии и
   своя секвенция. Это двигает модель изображений, и работы там больше, чем в
   модели склада.
4. **По каким свойствам вообще делятся неуникальные вещи?** Размер, цвет,
   принт, что-то ещё. Проектировать имеет смысл под известный список, а не под
   догадку.
5. **Нужно ли смешивать в одной корзине уникальные и неуникальные вещи?**
   Ответ «нет» многое упростил бы, но выглядит странно для покупателя.

### Мелочи, оставшиеся в этом разделе

- Удалить влитые ветки: на 9 сентября их **19**, все влиты в `main`.
- Запросы вида `WHERE "Product"."id" IN (NULL)` при пустом массиве.
- `Product.size` — свободная строка (в сиде `'M (Unisex)'`), по ней нельзя ни
  отсортировать, ни отфильтровать. Приводить к контролируемому значению
  **сейчас не нужно**: поле только показывается, а переделка в разработочной
  базе займёт минуты в тот момент, когда размеры реально понадобятся.

## Задача 7 — интерфейс проданного товара

**Статус:** не начата. Мелкая, чисто интерфейсная. От платёжного контура не
зависит, брать можно в любой момент.

**Что нужно.** На странице проданного товара не показывать кнопки «добавить в
корзину» и «добавить в избранное».

**Что происходит сейчас — хуже, чем просто лишние кнопки.**

`src/components/shared/product-page/product-info.tsx` рендерит обе кнопки
всегда. У корзины выставлено `disabled={!isAvailable}`, у избранного нет
никакой проверки статуса вообще.

Но `disabled` не работает: в
`src/components/shared/product-page/action-icon-button.tsx` настоящий атрибут
`disabled` закомментирован, а выставляется только `aria-disabled`. Кнопка
остаётся в порядке обхода табуляцией, сохраняет `cursor-pointer` и выглядит
совершенно обычной. Клик гасится уже внутри хука (`if (!isAvailable) return;`
в `src/hooks/use-product-actions.ts`), поэтому посетитель на странице
проданной вещи нажимает «в корзину» и **не получает ничего**: ни тоста, ни
сообщения, ни визуальной реакции. Выглядит как поломка сайта.

Избранное не проверяется нигде — проданную вещь можно положить в избранное, и
она там останется.

**Расхождение с каталогом.** В `card-footer-component.tsx` недоступный товар
показывает надпись «Sold Out» вместо иконки корзины. То есть в каталоге
посетитель понимает, что вещь продана, а на странице самого товара — нет.

**Что уже готово в коде.** Хук `useProductActions` возвращает `statusLabel`
со значениями `SOLD OUT`, `RESERVED` и `UNAVAILABLE`, но `product-info.tsx`
его не забирает. Готовый пример использования —
`src/components/shared/cart/add-to-cart-button.tsx`.

**О чём подумать при реализации.**

- Статусов три: `AVAILABLE`, `RESERVED`, `SOLD`. Нужно решить, ведёт ли
  `RESERVED` себя так же, как `SOLD`: вещь под бронью может вернуться в
  продажу через сорок минут, и прятать кнопки навсегда для неё неверно.
- Убрав кнопки, поставить на их место осмысленную метку, иначе блок действий
  просто исчезнет без объяснения. `statusLabel` для этого и предназначен.
- Заодно решить судьбу закомментированного `disabled` в
  `action-icon-button.tsx`. Он вводит в заблуждение и в каталоге тоже:
  `aria-disabled` без `disabled` означает, что скринридер объявит элемент
  недоступным, но он останется кликабельным и фокусируемым.

## Задача 8 — превью-деплои: OAuth и редиректы Stripe

**Статус:** закрыта 8 сентября 2026 решением **не делать**. Работы по ней не
предвидится; раздел оставлен, чтобы вопрос не поднимали заново.

**Решение владельца:** вход через Google и оплата Stripe остаются доступны
только на продакшене. Превью-деплои используются для проверки вёрстки и входа
по паролю — этого достаточно, усложнять ради них платёжный и OAuth-контур не
нужно.

**Что было на выбор и что отклонено.**

Вход через Google на превью технически недостижим без дополнительной
конструкции: Google принимает только заранее зарегистрированные
`redirect_uri`, а домен превью-деплоя меняется от сборки к сборке
(`art-jane-<хеш>-…vercel.app`). Рассматривались плагин `oauth-proxy` из
состава better-auth, который проводит OAuth через продакшен-домен и затем
передаёт сессию на превью, и ручная регистрация доменов веток
(`art-jane-git-<branch>-…vercel.app`, они стабильны в пределах ветки).
Оба варианта отклонены как избыточные.

Редиректы Stripe: `src/actions/checkout.ts` строит `success_url` и
`cancel_url` из `NEXT_PUBLIC_APP_URL`, одной на Preview и Production, поэтому
оплата, начатая на превью, вернёт покупателя на продакшен. Оставлено как есть
сознательно. Ничего не ломается — заказ проводится вебхуком, — просто
платёжный флоу проверяется на проде, как и раньше.

**Что из этого следует для будущих окон.** Не считать поломкой, что на
превью-деплое кнопка входа через Google уводит на продакшен, а оплата
возвращает туда же. Это ожидаемое поведение, а не недоделка.

## Задача 9 — дизайн модуля оформления заказа

Ссылка одна и всегда одна: новые экраны добавляются в неё, отдельные артефакты
не заводятся. Дизайн-система лежит вверху борда, экраны ниже.

### Визуальный язык — решения от 10 сентября 2026

**Стекло в духе Apple — осознанный выбор владельца, а не случайность.** Ранее
при переводе в светлую тему я стекло убрал, сославшись на то, что на белом фоне
размывать нечего. Наблюдение было верным, вывод — нет: правильно было не
отказываться от материала, а дать ему подложку.

- **Подложка** — тёплый янтарный градиент из трёх мягких пятен в гамме
  акцента `#f59e0b`, зафиксирован за всем приложением. Он не читается как
  картинка, его работа — дать стеклу цвет, который то подтягивает наверх.
- **Формула одна на всё приложение**, три высоты: плёнка (blur 12, липкая
  шапка), панель (blur 20, карточки и шторки), шторка (blur 40, модалки).
  Ключевой ингредиент — **`saturate(180%)`**: без него размытие даёт серую
  муть. Светящаяся кромка сверху — `inset 0 1px 0`.
- **Стекло — только плавающий слой.** Шапка, шторки, диалоги, липкая сводка
  заказа, плавающие кнопки. Содержимое — фотографии, текст, списки — плотное.
  Если стеклянное всё, глубина исчезает.
- **Поля ввода — ниши, не стекло.** Заливка темнее подложки плюс внутренняя
  тень. Стекло в стекле даёт молоко.
- **Главное действие плотное.** Кнопка оплаты не стеклянная: она обязана быть
  громкой.
- **Не больше трёх-четырёх стёкол на экране** — `backdrop-filter` дорогой.
- **`prefers-reduced-transparency`** уважается: размытие снимается, стекло
  становится плотной заливкой.
- **Обе темы спроектированы в токенах, в бой выпускается пока только
  светлая.** Тёмная — не инверсия: тёмный тинт со светлой кромкой сверху.
- **Язык интерфейса — русский на всём приложении.**
- У логотипа вверху страниц **сохраняется тень**.

### Состав модуля — восемь экранов

Разбор по коду показал, что экранов заметно больше, чем файлов.

| №   | Экран                           | Откуда                      | Состояние |
| --- | ------------------------------- | --------------------------- | --------- |
| 1   | Форма заказа                    | `checkout/page.tsx`         | нарисован |
| 2   | Состояния сводки заказа         | `checkout-aside.tsx`        | нарисован |
| 3   | Успех — `PaidView`              | `checkout/success/page.tsx` | нарисован |
| 4   | Успех — `ProcessingView`        | там же                      | нарисован |
| 5   | Успех — `UnconfirmedView`       | там же                      | нарисован |
| 6   | Оплата отменена                 | `checkout/cancel/page.tsx`  | нарисован |
| 7   | Корзина не загрузилась          | `checkout/error.tsx`        | нарисован |
| 8   | Модалка ошибки — семь состояний | `checkout-error-dialog.tsx` | нарисован |

**Страница успеха — это три экрана, а не один.** Один адрес
`/checkout/success?session_id=…`, но три исхода: оплата получена; платёж ещё
идёт при отложенном способе оплаты; заказ не подтверждён — чужая ссылка, гость
или уже отменённый заказ.

**Модалка ошибки — самая трудоёмкая часть.** Восемь кодов дают семь состояний:
`VALIDATION_ERROR`, `STRIPE_ERROR` и `INTERNAL_ERROR` сходятся в один запасной
текст, зато `PRODUCT_UNAVAILABLE` раздваивается — со списком позиций и без него
это два разных окна, — а `EMPTY_CART` по решению от 11 сентября отделён от
`CART_CHANGED` в собственное окно. У `PRODUCT_UNAVAILABLE` внутри строится
список товаров с индивидуальными причинами по каждому.

### Порядок работ

1. ~~**Успех — все три вида.**~~ Сделано 10 сентября.
2. ~~**Отмена оплаты.**~~ Сделано 11 сентября.
3. ~~**Модалка ошибки и экран несработавшей загрузки корзины.**~~ Сделано
   11 сентября. Состояний вышло семь, а не шесть: `EMPTY_CART` отделён от
   `CART_CHANGED` — см. решения ниже.
4. **Перенос макетов в код.** Начинается только после того, как владелец
   признает дизайн готовым. Единственное место, где работа выходит за
   пределы вёрстки, — экран отмены: он становится серверным компонентом и
   читает корзину.

### Решения по замечаниям владельца к борду, 11 сентября

Замечания оставлены комментариями прямо на макетах страницы успеха. Принятое:

- **Логотип на странице успеха остаётся.** Она была единственной в модуле без
  него: в коде там рендерится только `ButtonGoHome`. Владелец согласился —
  «логотип должен быть на этой странице».
- **Кнопка называется «Вернуться в магазин»**, а не «В каталог». Формулировка
  общее и не привязана к разделу каталога.
- **Решено, куда она ведёт: `/shop`.** `ButtonGoHome` по умолчанию ведёт на `/`
  (`src/components/shared/button-go-home.tsx:21`), а главная у нас и есть
  витрина: герой плюс категории по четыре товара. Полный каталог с фильтрами
  живёт отдельно на `/shop`. Текстовая кнопка на `/` дублировала бы
  иконку-домик в углу, поэтому роли разведены: **иконка-домик → `/`,
  «Вернуться в магазин» → `/shop`**. Человек после покупки или отмены попадает
  туда, где выбирают вещи, а не проходит герой-блок заново.
- **На «Платёж обрабатывается» добавлена вторая кнопка** — «Вернуться в
  магазин» рядом с «Мои заказы», чтобы экран не был тупиком. Иерархия та же,
  что на «Оплата получена»: «Мои заказы» основная, вторая второстепенная.
- **Итоговая строка называется «Итого», а не `Total`.** В коде там английское
  слово — единственное на всей русской странице.

### Решения по экрану отмены, 11 сентября

Экран отмены — самый простой в модуле: `src/app/checkout/cancel/page.tsx` это
33 строки без единого обращения к базе. Снимает бронь не он, а
`src/app/api/checkout/cancel/route.ts`, и **редиректит он без параметров** — то
есть страница отмены сегодня физически ничего не знает о заказе.

- **Тон: прямо, но без давления.** Экран не ошибка — человек сам нажал «назад».
  Красных тревожных знаков нет. Но то, что бронь снята и вещь в единственном
  экземпляре снова доступна всем, говорится прямо, одной спокойной строкой.
  Никаких таймеров и счётчиков «смотрят три человека» — для магазина такого
  уровня это читается как приём дешёвых распродаж.
- **Первым делом на экране — «деньги не списаны».** Именно это человек хочет
  узнать в первую очередь, и именно этого в текущем тексте нет вообще.
- **Формулировка «деньги не списаны» утверждена 11 сентября** и остаётся как
  есть. Решение владельца: «мы не списываем, значит, не списались». Проверено,
  что для нашего набора способов оплаты это буквальная правда: в
  `src/actions/checkout.ts` задано `payment_method_types: ['card']` со
  списанием сразу, и на пути отмены платёж вообще не подтверждается — банку
  нечего замораживать. Оговорка про холд («если банк успел заморозить сумму,
  она вернётся автоматически») понадобится только если появятся способы
  оплаты с отложенным подтверждением, вроде SEPA или Klarna.
- **Показываем корзину, а не отменённый заказ.** `releaseOrder` в
  `src/lib/orders.ts` корзину не трогает — возвращает товарам статус
  `AVAILABLE` и ставит заказу `CANCELLED`, не более. Поэтому корзина цела,
  и именно из-за этого кнопка «Оформить заново» работает. Читать корзину
  дешевле, чем искать отменённый заказ, и полезнее: видно **актуальные**
  статусы вещей, в том числе что одну уже успели купить.
- **Работа по коду, которую это влечёт, согласована владельцем 11 сентября:**
  страница отмены становится серверным компонентом и читает корзину. Сегодня
  она статическая. Это единственный экран модуля, где дизайн требует новых
  данных, а не только новой вёрстки. Кнопка «Убрать» на недоступной позиции
  переиспользует существующий
  `src/components/shared/checkout/remove-button.tsx` из чекаута, так что своей
  логики удаления писать не придётся.

### Решения по модалке ошибки, 11 сентября

Разобран `src/components/shared/checkout/checkout-error-dialog.tsx`.

- **Красный остался только там, где вещь потеряна навсегда** — на «Некоторые
  товары недоступны». Раньше красный треугольник и красная кнопка стояли на
  всех четырёх кодах из `CRITICAL_CODES`, включая бытовые «Корзина
  изменилась» и «Время сессии истекло». Остальные шесть состояний янтарные.
- **Незакрываемость отделена от цвета.** Это разные механики: цвет говорит,
  насколько всё плохо, а замок — поедет ли оформление дальше. Все четыре
  критичных кода по-прежнему не закрываются кликом мимо, но выглядят спокойно.
- **Кнопка «Убрать» на каждой недоступной позиции.** Владелец выбрал вариант
  «по одной позиции», без общей кнопки «убрать все». Сейчас текст говорит
  «Удалите их из корзины», а удалять надо идти самому в сводку заказа — тот же
  разрыв, что был найден на экране отмены. Переиспользуется существующий
  `remove-button.tsx`.
- **Причины разведены цветом.** «Продана — вещь в единственном экземпляре»
  красным, «Забронирована другим покупателем, освободится в течение 40 минут»
  янтарным. Разница принципиальная: в первом случае ждать бессмысленно.
- **Имя вещи переносится на две строки, а не обрезается многоточием.** При
  первой сборке макета название резалось на 131 пиксель, и выходило
  «Distressed T-Shirt «Guar…» — терялся номер экземпляра. Список существует
  ровно затем, чтобы покупатель узнал, какая вещь недоступна.
- **ID ошибки стал пилюлей с копированием**, как номер заказа на экране
  успеха. Раньше это была почти невидимая серая строка, которую человек
  переписывает в поддержку руками.
- **Кнопка «Войти» перестала быть красной.** В коде у неё
  `variant="destructive"`, а красная кнопка в языке интерфейсов означает
  необратимое разрушение, а не вход в аккаунт.
- **Третья, вложенная ветка `PRODUCT_UNAVAILABLE` переписана.** Если список
  пришёл, но ни один `id` не совпал с позициями корзины, покупателю
  показывалось «(Товары из корзины обновлены)» курсивом в скобках и кнопка
  «Понятно», которая ничего не решает. Решено показывать в этом случае второе
  окно — «Состав каталога изменился» с «Обновить страницу».
- **`EMPTY_CART` получил седьмое, собственное окно.** Он делил текст с
  `CART_CHANGED` — «Корзина изменилась… давайте обновим данные», — хотя
  корзина не изменилась, а опустела. Обновление возвращало на `/checkout`, где
  гарда на пустую корзину нет, и человек видел форму заказа без единой вещи.
  Теперь это «Корзина опустела» с единственной кнопкой «В магазин»: при
  `CART_CHANGED` покупатель остаётся оформлять заказ, при `EMPTY_CART` ему
  здесь делать нечего.

### Решения по экрану несработавшей загрузки корзины, 11 сентября

`src/app/checkout/error.tsx` — граница ошибок сегмента, ловит сбой чтения
корзины на `/checkout` (страница читает базу без `try/catch` — это решение
задачи 1).

- **Знак янтарный, не красный.** Ничего не потеряно, сбой скорее всего
  временный.
- **Добавлена плашка «Вещи из корзины никуда не делись».** Первый страх
  человека на этом экране — что он потерял заказ.
- **Показывается `error.digest`** — короткий отпечаток, по которому сбой
  находится в логах сервера. Next.js передаёт его в компонент, и сейчас он
  приходит в пропсах и никак не используется. Владелец согласился 11 сентября.
  Показывать отпечаток безопасно: это хеш, деталей сбоя он не раскрывает.
- **Появился второй выход — «Вернуться в магазин».** Оговорка записана прямо
  на макете, и формулировать её нужно точно. Сам экран ошибки базу не читает и
  отрисуется всегда — он статический. Читает базу **страница, куда ведёт
  кнопка**: при полном отказе базы человек упрётся там в такую же ошибку. Но
  сбой может быть и частным, только в запросе корзины, — тогда переход
  сработает. Второй выход всё равно лучше тупика с одной кнопкой.

### Адаптив, 11 сентября: решения и механика

Владелец указал, что нарисован пока только десктоп, и попросил переключатель
устройств в шапке борда — как переключатель темы. Сделан переключатель и
переведены на адаптив шесть экранов из восьми.

**Границы взяты из проекта, а не выдуманы.** Tailwind 4 без своих `screens`,
значит действуют дефолтные. В чекауте используются две: `lg` = 1024, на нём
`checkout/page.tsx` включает вторую колонку, и `sm` = 640, на нём
`checkout-form.tsx` ставит поля парами.

**Отсюда неочевидное следствие: iPad в портрете — это «широкий мобильный».**
834 меньше 1024, поэтому планшет в портрете получает одноколоночную раскладку,
как телефон, только поля формы идут парами. Десктопную раскладку планшет
получает лишь в альбоме, с 1194. Три выбранные ширины дают три честно разные
картинки: 1440 — две колонки, 834 — одна колонка с парными полями, 390 — одна
колонка с полями по одному.

**Медиазапросы внутри макетов не работают, и это не мелочь.** Макет на борде —
элемент фиксированной ширины внутри страницы, а `@media` смотрит на ширину окна
браузера. Поэтому адаптив сделан контейнерными запросами, привязанными к ширине
артборда. Помимо того, что это единственный работающий способ, он ещё и не даёт
соврать: один и тот же код обязан ужиться на всех трёх ширинах, как потом в
настоящей вёрстке. Отдельные картинки под каждое устройство позволили бы
нарисовать то, что в вёрстке не соберётся.

**Контейнером должна быть обёртка, а не сам макет.** Контейнерный запрос
стилизует потомков контейнера, но не сам контейнер — иначе правило зависело бы
от размера, на который само влияет. Первая сборка ставила `container-type` на
подложку, и правила для `.su-page` молча не применялись, хотя правила для
вложенных элементов работали. Свойство перенесено на `.bd-inner`.

**Принятые решения по содержанию:**

- **Планшет — 834, портрет iPad.** Это реальная зона риска: одна колонка, как
  на телефоне, но вдвое шире, и всё растягивается некрасиво, если не проверить.
- **Липкая нижняя панель на мобильном обсуждена повторно 24 сентября и
  отклонена.** Сначала решение было в её пользу, но после разбора кода
  владелец выбрал классику: форма, под ней сводка, под ней кнопка — ровно как
  сейчас. Решающий довод: форма работает в режиме `mode: 'onChange'`
  (`checkout-form.tsx:80`), и кнопка оплаты заблокирована, пока не заполнены
  все девять полей. Липкая панель висела бы внизу мёртвой почти всё время
  заполнения — около 70 пикселей экрана, занятых неактивной кнопкой, которая
  вдобавок ничем не отвечает на нажатие и не подсказывает, какое поле не
  заполнено. Плюс это новый компонент, которого нет в коде: безопасная зона
  на iPhone, нижний отступ страницы, дублирование суммы и состояния.
  Отклонено и предложение поднять сводку над формой на узких экранах —
  оставляем порядок как в коде.
- **Имя вещи на узких экранах переносится, а не режется многоточием.** То же
  решение, что было принято для списка в модалке.

**Две ловушки вёрстки, пойманные при сборке** (обе — причина, по которой
адаптив нельзя «нарисовать», его нужно проверять):

- Высоту содержимого замеряли до выставления новой ширины, поэтому сцена
  оставалась прежней высоты и обрезала перестроенный макет. Порядок операций
  исправлен: сначала ширина, потом замер.
- У колонки `.su-col` горизонтальные поля `auto`. В обычном блоке они
  центруют, а во флексбоксе **отключают растягивание**: элемент начинает
  считать ширину по содержимому и вылезает за артборд. На телефоне поля
  убраны, на планшете оставлены — там ширина 672 по центру даёт комфортную
  длину строки.

**Шаг 1 закрыт 24 сентября: форма заказа переведена на адаптив.** Раскладка
снята с кода, а не придумана: контейнер `max-w-7xl` (1280) на артборде 1440
даёт боковые поля 80; `lg:grid-cols-5` с `col-span-3` и `col-span-2` делит
колонки 739 и 493 при `gap-12`; боковые отступы страницы идут по
`px-4 sm:px-6 lg:px-12`, то есть 16, 24 и 48. Ниже 1024 колонка одна и сводка
уезжает под форму, ниже 640 поля формы встают по одному.

Два расхождения, найденные при сборке:

- **Колонки делились 650/582 вместо 739/493.** Причина та же, что уже ловили в
  модалке: голый `fr` — это `minmax(auto, fr)`, и колонка со сводкой
  раздвигалась по содержимому. Исправлено на `minmax(0, 3fr) minmax(0, 2fr)`.
  Важно, что дефект был именно в макете: раскладка выглядела правдоподобно,
  пока не сверили с кодом.
- **На честной ширине сводки название вещи обрезается на 89 пикселей.** В
  `checkout-aside.tsx:117` у названия стоит `truncate`, и при колонке 493 (а не 582) пропадает номер экземпляра — единственное, что отличает одну вещь от
  другой. **Согласовано 24 сентября:** название переносится на две строки,
  и не только в сводке — обрезку убрали из строк товара во всём модуле, на
  всех ширинах. Формулировка владельца: «чтобы везде было в одинаковом стиле
  и чтобы человек мог прочитать название». Это расхождение с кодом:
  `truncate` придётся убрать и в `checkout-aside.tsx`.

На макете формы стоит и вторая пометка, зелёная: на 834 и 390 кнопка
«Перейти к оплате» оказывается в самом низу страницы, и это **принятое
решение**, а не недосмотр — см. разбор липкой панели выше.

**Шаг 2 закрыт 24 сентября: состояния сводки переведены на адаптив. Все
восемь экранов модуля теперь адаптивны.**

Этот макет — не страница, а лист образцов: три состояния сводки рядом и
четыре подписи кнопки оплаты. Поэтому адаптив у него двойной. Сама витрина
должна читаться на узком борде: три образца в ряд превращаются в один, четыре
подписи кнопки — в два ряда на планшете и в столбик на телефоне. И, что
важнее, **ширина образца обязана совпадать с реальной шириной сводки** на том
же устройстве, иначе лист врёт о переносах строк. На планшете и телефоне
совпадение точное — 786 и 358. На десктопе образец уже настоящего на 85
пикселей (408 против 493), потому что три состояния стоят рядом ради
сравнения; это оговорено прямо на листе, а не оставлено расхождением.

Заодно из `.su-row p` убрана обрезка многоточием, которая до этого снималась
только на узких ширинах: на экране отмены при 1440 название всё ещё резалось.
Теперь приём единый во всём модуле на всех ширинах.

**Задача 9 по рисованию закрыта.** Осталось признание дизайна готовым и
перенос в код.

## Задача 10 — номер заказа: его не существует как сущности

**Статус: заведена 11 сентября 2026, чтобы не забыть. Решения нет.**

Появилась из замечания владельца на макете страницы успеха: там показан «Номер
заказа 31C8FFB6», и возник вопрос, есть ли этот номер в базе. Проверено по
схеме и коду, а не по памяти.

**Отдельного поля с номером заказа в базе нет.** У модели `Order` в
`prisma/schema.prisma` единственный идентификатор — первичный ключ
`id String @id @default(uuid())`. Ни одна из шести миграций ничего похожего на
номер не добавляла.

То, что покупатель принимает за номер, считается на лету из этого uuid —
`src/app/checkout/success/page.tsx:35`:

```ts
const orderNumber = order.id.split('-')[0].toUpperCase();
```

Это первые восемь шестнадцатеричных символов uuid в верхнем регистре. Нигде не
хранится, ничем не гарантируется, в базе по нему не найти.

Та же формула скопирована руками во второе место —
`src/components/shared/profile/order-card.tsx:73`, — но выводится там с
префиксом «ID: ». Покупатель видит одну и ту же строку под двумя разными
названиями: на успехе это «Номер заказа», в профиле «ID».

### Что из этого следует — три разных по весу вопроса

1. **Расхождение в названиях.** Одна и та же строка называется «Номер заказа»
   и «ID». Чинится переименованием, стоит десять минут.
2. **Формула продублирована.** Поменяем усечение в одном месте — во втором
   останется старое, и клиент с поддержкой будут сверять разные строки.
   Лечится выносом в одну функцию.
3. **Уникальность не гарантирована базой.** Восемь hex-символов — это четыре
   миллиарда значений, но по парадоксу дней рождения совпадение становится
   вероятным задолго до исчерпания: при нескольких десятках тысяч заказов —
   уже ощутимо. Для магазина единичных вещей это очень далеко, поэтому в
   ближайшее время не проблема. Настоящее ограничение в другом: это усечение
   первичного ключа, а не самостоятельное поле с `@unique`, поэтому база не
   мешает двум заказам получить один и тот же «номер».

**Чего у нас нет и что стоит обсудить отдельно:** человекочитаемого номера
вида `JA-2026-0042`. uuid не последователен, поэтому ни клиент не может сказать
«мой заказ сороковой», ни мы по номеру понять, когда он был. Это не поломка, а
отсутствующая возможность.

## Задача 11 — письмо-подтверждение заказа

**Статус: обсуждается 11 сентября 2026.**

Появилась оттуда же: на макете страницы успеха есть строка «Письмо с
подтверждением ушло на …», и владелец заметил, что отправки писем, кажется, нет.

**Подтверждено: проект не отправляет ни одного письма.** В `package.json` нет
ни одной почтовой библиотеки — ни `resend`, ни `nodemailer`, ни `sendgrid`, ни
`postmark`, ни SES. Значит строка на макете обещает то, чего не происходит, и в
таком виде в код её переносить нельзя.

**Адрес у нас при этом есть.** `Order.customerEmail` заполняется реальным
адресом из формы заказа (`src/actions/checkout.ts`, создание заказа), и тот же
адрес уходит в Stripe как `customer_email`. То есть отправлять есть куда и есть
что: в заказе лежат состав, суммы на момент покупки и адрес доставки.

**Готовая точка для отправки тоже есть.** `fulfillOrder` в `src/lib/orders.ts`
возвращает `true` только тому вызову, который реально перевёл заказ из `PENDING`
в `PAID`, и `false` — всем повторным. Это ровно одно срабатывание на заказ,
несмотря на то что функцию вызывают из трёх мест: вебхук, страница успеха и
cron. Дублей писем при ретраях вебхука не будет без всякого дополнительного
флага.

### Варианты, разобранные при обсуждении

- **Включить квитанции Stripe.** Ноль строк кода и ноль евро: в настройках
  Stripe есть отправка письма об успешном платеже, а `customer_email` мы уже
  передаём. Минус — это квитанция от Stripe, без нашего бренда и без адреса
  доставки. В тестовом режиме реальным адресатам не уходит.
- **Своё письмо через Resend.** Бесплатный потолок — три тысячи писем в месяц,
  вёрстка на React Email тем же стеком, что и сайт. Требует своего домена с
  SPF и DKIM в DNS, иначе письма уходят только на собственный адрес.
- **SMTP через nodemailer.** Дешёво, но письма магазина с обычного почтового
  ящика попадают в спам и упираются в лимиты отправки. Для магазина плохой
  вариант.

### Предложенный порядок

Сначала **включить квитанции Stripe** — минута работы и ноль евро, зато у
покупателя на руках появляется документ о списании денег, что важнее всего в
худшем сценарии, когда заказ не подтвердился. Своё брендированное письмо —
позже, и сразу вместе с письмом об отправке: про оплату покупатель и так знает,
он только что нажал кнопку, а письма «вещь отправлена, вот трек» он реально
ждёт. Решения по этому порядку владелец пока не принимал.

### Открытые вопросы

- **Есть ли домен, с которого можно отправлять.** Вопрос задан 11 сентября,
  ответа пока нет. От него зависит, реален ли Resend уже сейчас или начинать
  придётся с квитанций Stripe.
- Нужно ли письмо сейчас, если заказ и так виден в профиле: чекаут требует
  авторизации, поэтому покупатель всегда найдёт свой заказ у себя.
- Что первее — подтверждение оплаты или письмо об отправке с трек-номером.
  Статус `SHIPPED` в схеме есть, а интерфейса, который его ставит, нет.

## Задача 12 — дизайн остальных экранов

**Заведена 24 сентября 2026.** Владелец принял дизайн модуля оформления
заказа целиком — «всё прошло прекрасно», включая поведение на разных экранах и
в обеих темах, — но **перенос в код отложил**: сначала довести до единого стиля
всё приложение, и только потом трогать код. Задача 9 остаётся закрытой по
рисованию и ждёт своей очереди на перенос.

### Главное, что выяснилось при разборе проекта

**Стекло уже в коде, в шестнадцати файлах.** `backdrop-blur` стоит в
`product-card`, обеих шторках, `glass-tabs`, `mobile-fabs`, галерее товара,
`profile-header`, `order-card`, `category-section`, `auth-dialog`,
`product-status-badge` и других. То есть мы **не навязываем проекту новый
стиль, а приводим в порядок уже существующий**: сейчас он просто разный —
разный блюр, разная подложка, всё на тёмной теме. Это сильно меняет оценку
объёма: не «перерисовать приложение», а «свести к одной формуле».

**Глобальной шапки нет.** `layout.tsx` рендерит только `ShopStoreProvider`,
`GuestSyncBridge`, `Toaster` и `MobileFabs`. Навигацию каждая страница
приносит свою: `StickyNav` на главной, `CheckoutHeader` в чекауте, где-то
просто логотип. Это и есть причина, по которой приложение может ощущаться
разным, даже когда все экраны хороши по отдельности.

**Уведомления не нарисованы вообще.** `Toaster` (sonner) висит в `layout.tsx`
и всплывает на каждое действие — добавили в корзину, удалили, ошибка. Сквозной
элемент, которого мы ни разу не касались.

### Решения владельца, 24 сентября

- **Порядок — «от оплаты назад».** Сначала закрываем стык с чекаутом, дальше
  идём против течения покупателя. Каждый следующий шаг опирается на уже
  сделанное.
- **Шапку в одну не сводим.** Остаётся постранично, просто в едином стиле.
  Выбор в пользу меньшего объёма правок в коде потом; риск снова разъехаться
  принят осознанно.
- **Сквозная фурнитура идёт первым заходом**, вместе со шторками: уведомления
  чаще всего всплывают именно на действиях с корзиной и избранным, и рисовать
  их рядом с тем, что их вызывает, естественнее.

### План по шагам

1. ~~**Шторки корзины и избранного плюс сквозная фурнитура.**~~ Сделано
   24 сентября. Шторка корзины —

   обрыв, который увидит каждый покупатель без исключения. В ней уже лежат все

2. ~~**Страница товара.**~~ Сделано 24 сентября. Здесь принимается решение о покупке. Единственный
   экран, где стекло ложится **на фотографию** — то, ради чего этот приём и

4. ~~**Профиль**~~ — три вкладки: избранное, корзина, история заказов.

### Шаг 1 закрыт 24 сентября: шторки и сквозная фурнитура

Нарисованы три листа: шторка корзины в трёх состояниях, шторка избранного в
двух и лист уведомлений с кнопками на телефоне. Все адаптивны, проверены на
1440, 834 и 390.

**Шторка целиком на английском.** «CART», «{n} items», «Your cart is empty»,
«CONTINUE SHOPPING», «TOTAL», «CHECKOUT», «SIGN IN TO CHECKOUT», «Size:», а в
избранном ещё «FAVORITES», «Your wishlist is empty» и «DISCOVER ART». Это
экран **прямо перед** полностью русским оформлением заказа. Переведено всё.
Отдельно отмечено требование, которого в коде нет: счётчик «2 items» на
русском требует склонения — одна вещь, две вещи, пять вещей.

**Кнопка оформления названа так же, как в сводке заказа** — «Перейти к
оплате». Это буквально одно и то же действие, и называться оно должно
одинаково.

**Строки внутри шторки — ниши, а не стекло.** Правило, уже применённое в
модалке ошибки и в сводке: стекло поверх стекла запрещено дисциплиной. Сама
шторка при этом стекло верхнего уровня, `blur 40`.

**Ширина образцов настоящая — 448**, как даёт `sm:max-w-md`, поэтому переносы
строк на макете такие же, как будут в жизни. Ниже 640 шторка занимает весь
экран, как `w-full` в коде.

#### Найденные расхождения и решения

- **Удаление сообщается через `toast.error`.** Красная плашка с
  восьмиугольником, как настоящая ошибка, — на намеренное и обратимое действие
  покупателя. Четыре вызова: по два в `product-info.tsx` и
  `card-footer-component.tsx`. **Согласовано 24 сентября:** заменяется на
  нейтральное уведомление.
- **Кнопка удаления в строке красная** — иконка с `fill-red-500` в красном
  кружке. Красный в нашем языке означает потерю навсегда, а убрать вещь из
  корзины можно и передумать. **Согласовано 24 сентября:** нейтральная.
- **Счётчик в шапке шторки приходит пропсом, а список из стора.** Два
  источника одной правды: разойдутся — шапка соврёт о числе вещей. Нейтральная
  заметка на макете.
- **Число вещей на кнопках телефона стояло по центру иконки**, поверх сердца
  и корзины. Вопрос был задан прямо — не осознанный ли это приём. **Ответ
  владельца 24 сентября: оставляем угловой счётчик.** Центральное число
  спорило с самим знаком, угловое не мешает иконке читаться.

#### Уведомления: чего не было вообще

Двадцать два вызова в коде, и ни одного нарисованного макета. Сейчас плашка
заливается плоским цветом целиком — изумрудным, розовым, синим или янтарным.
**Синий в тёплом мире проекта чужой**, а сплошная заливка спорит со стеклом
всего остального. На макете плашка стеклянная, а тип несёт цветной знак.
Найдено и единственное английское уведомление: «Failed to sync your cart» в
`guest-sync-bridge.tsx`.

#### Кнопки на телефоне: появилась иерархия

Сейчас обе залиты одним янтарным, и внутри левой красное сердце — два ярких
цвета спорят друг с другом. Корзина — то, ради чего человек пришёл, поэтому
осталась янтарной и плотной; избранное вспомогательное, поэтому стеклянное.
Размеры выровнены: в коде они 48 и 56 без причины. Отступы сделаны
симметричными: сейчас левая прижата к самому краю экрана (`left-0`), а правая
отстоит на четыре пикселя (`right-1`).

**Все решения по шагу 1 приняты владельцем 24 сентября**, и вместе с ними
закрыта последняя пометка по всему борду — та, что висела с 11 сентября на
экране «Заказ не подтверждён»: текст обещал «напишите нам», а связаться было
не с чего. **Решение: кнопка «Написать нам» ведёт на новую страницу «О нас»**
с рассказом о художнике и контактами владельца. Розовых пометок на борде не
осталось ни одной.

### Новая страница «О нас»

**Такой страницы в проекте не существует.** Маршруты сегодня: `/`, `/shop`,
`/product/[slug]`, `/profile`, `/checkout` и `not-found`. Это первая **новая**
страница за всю работу — не переделка существующей, а новый маршрут,
новая вёрстка и новое содержание.

Что она решает сразу:

- даёт адресата обещанию «напишите нам» на экране «Заказ не подтверждён»;
- закрывает вопрос, которого у магазина единичных вещей быть не должно: кто
  автор. Человек платит 150 € за вещь в единственном экземпляре и сейчас не
  может узнать о том, кто её сделал, ничего;
- становится местом для контактов, которых в проекте нет нигде.

**Чего не хватает и чего я придумать не могу:** текста о художнике, фотографий
и настоящих контактов. Это не дизайнерское решение, а содержание, которое
может дать только владелец. Макет будет нарисован с явно помеченными
заглушками, чтобы видно было, где чужой текст, а где настоящий.

### Шаг 2 закрыт 24 сентября: страница товара

Два листа: «Товар · в наличии» и «Товар · продана и забронирована». Оба
адаптивны, проверены на 1440, 834 и 390. Для галереи скачана настоящая
фотография товара из Supabase и вписана в 3:4 — весь смысл этого экрана в
том, что стекло ложится на снимок, а не на заливку.

**Задача 7 оказалась хуже, чем была записана, и проще в починке.** В плане
стояло, что кнопка «в корзину» на проданной вещи «выглядит рабочей и молча
ничего не делает». Механизм такой: в `action-icon-button.tsx` проп `disabled`
**закомментирован**, остался только `aria-disabled`, который для мыши не
значит ничего. Кнопка выглядит обычной и нажимается обычно, а в
`use-product-actions.ts` стоит тихий `if (!isAvailable) return;`. Человек
жмёт — не происходит ничего, ни ошибки, ни объяснения. Жмёт ещё раз.

**Почти всё для починки уже написано.** Хук отдаёт `statusLabel` —
`SOLD OUT` / `RESERVED` / `UNAVAILABLE`, — и страница товара его не
использует. В проекте есть готовый `ProductStatusBadge`, уже стеклянный и
янтарный, но живёт он только на карточках каталога.

#### Решения владельца, 24 сентября

- **Главное действие получило подпись.** Была красная иконка корзины без слов
  (`variant="destructive"` на добавлении в корзину — третий случай этого
  приёма не по назначению). Стала янтарная кнопка «В корзину» плюс стеклянный
  квадрат с сердцем: та же иерархия, что у кнопок на телефоне.
- **На проданной вещи вместо кнопки — объяснение и переход к похожим.** Бейдж
  «Продана» на фотографии, панель с текстом о единственном экземпляре и
  кнопка «Похожие вещи», ведущая к блоку рекомендаций, который на странице уже
  есть. Человек не упирается в тупик.
- **Сердце на проданной вещи остаётся рабочим.** Отметить — это не покупка, а
  закладка; в шторке избранного такая вещь уже помечена бейджем «Продана».

#### Разница двух недоступных статусов теперь читается цветом

**Продана** — навсегда, ждать бессмысленно: бейдж и знак красные. **Забронирована**
— чужая бронь, спадёт максимум через сорок минут: янтарные. В коде оба
состояния сейчас показываются одним янтарным бейджем. На листе оба бейджа
стоят рядом, чтобы разница была видна, а не заявлена.

#### Прочие находки

- **Две английские строки:** «Description is temporarily unavailable.» —
  запасной текст описания, и «Size» — подпись характеристики. Плюс
  `statusLabel` выдаёт `SOLD OUT` по-английски.
- **Другая точка перелома, чем в чекауте.** Страница товара разъезжается на
  две колонки с **768** (`md:grid-cols-2`), а оформление заказа — с 1024.
  То есть на iPad в портрете товар уже двухколоночный, а чекаут ещё нет.
  Макет это повторяет честно, но знать об этом надо.
- **`hasThreeSixty={true}` зашит жёстко** с комментарием «можно включить
  жестко для теста». По схеме `sequenceFolder` не nullable, поэтому вкладка
  360° включена у всех товаров всегда.
- **Карточка в блоке рекомендаций нарисована предварительно.** Её настоящий
  вид — предмет шага 3, где она делается один раз для каталога и главной.
  На листе стоит оговорка.

### Шаг 3 закрыт 24 сентября: карточка, каталог и главная

Три листа: «Карточка товара · четыре состояния», «Каталог», «Главная». Все
адаптивны, проверены на 1440, 834 и 390. Карточка рисовалась первой и один
раз — она общий атом обеих страниц.

**Приём владельца сохранён и уточнён.** В `product-card.tsx` блок с описанием
наезжает на низ фотографии (`-mt-5`) и сделан стеклом (`backdrop-blur-md`).
Это ровно тот случай, ради которого стекло и существует — полупрозрачный слой
поверх снимка, а не поверх заливки. Оставлено как есть по существу, приведено
к формуле дизайн-системы по цифрам.

**Сетки повторяют код, а не придуманы.** Каталог — 1 / 2 / 3
(`sm:grid-cols-2 lg:grid-cols-3`), главная — 1 / 2 / 4
(`sm:grid-cols-2 lg:grid-cols-4`). Плотности разные; **вопрос, намеренно ли**,
оставлен пометкой на листе главной.

#### Что изменилось в карточке

- **Карточка собрана в один цельный объект — правка по замечанию владельца
  24 сентября.** В первой версии подиум имел боковые отступы в 12 пикселей и
  своё скругление, из-за чего читался как оторванный от фотографии кусок.
  Владелец сравнил со своим оригиналом на `art-jane.vercel.app`: «в оригинале
  это как одна сплошная карточка». Теперь скругление и обрезка живут на самой
  карточке, подиум идёт во всю её ширину и по-прежнему наезжает на фотографию
  на 28 пикселей — наезд владельцу нравится и сохранён.
- **Бейдж «Продана» больше не срезает скруглённый угол.** Он стоял в левом
  верхнем углу с квадратным углом и превращал закруглённый угол карточки в
  прямой. Теперь его верхний левый угол повторяет скругление карточки.
- **Стрелки перелистывания лицо-спина стоят на фотографии** маленькими
  стеклянными кружками, как в галерее товара. В коде это отдельный ряд внутри
  карточки: два серых круга по 48 пикселей, шире и заметнее самого названия
  вещи. В первой версии борда стрелок не было на листах каталога и главной —
  владелец это заметил, теперь они есть на всех одиннадцати карточках.
  **Размещение согласовано 24 сентября:** остаётся вариант со стеклянными
  кружками на фотографии. Уточнение владельца: **стрелки показываются только
  при наведении мыши.** На телефоне и планшете, где мыши нет, стрелок не
  должно быть вообще — там человек листает свайпом.
- **Те же три решения, что на странице товара:** красные `variant="destructive"`
  уходят, фальшивая блокировка (`aria-disabled` без `disabled`) заменяется
  явной подписью, английское «Sold Out» и «Size : » (с пробелом перед
  двоеточием) переводятся.
- **У брони показано время, до которого она держится.** Поле
  `Product.reservedUntil` в базе есть и в интерфейсе не используется нигде.
  «Бронь до 18:40» полезнее, чем просто «забронирована».
- **Обе стрелки вызывают один и тот же `toggleSide`.** Сторон всего две, так
  что работает верно, но две стрелки обещают карусель из многих кадров.
  Нейтральная заметка.

#### Английские строки, найденные на этом шаге

«Shop Archive» — заголовок каталога, при русском подзаголовке под ним.
«The archive is empty. New works will appear soon.» — пустая витрина на
главной, тогда как пустая категория в каталоге сообщает то же самое
по-русски. «Load more (N)», «Show all (N)», «Collapse», «Loading…» — все
кнопки секций на главной. «Sold Out» и «Size : » — на карточке.

Заголовок каталога предложен как **«Архив»**: слово держит смысл магазина
единичных вещей лучше, чем «Каталог». Помечено предложением.

### Замечания владельца к главной, 24 сентября

Владелец сравнил лист «Главная» с работающим сайтом и забраковал обе верхние
части. Разбор ниже сделан до правок.

**Герой нарисован неверно.** На сайте над первым блоком стоит не статичная
фотография, а **последовательность кадров, которую листает прокрутка**:
`HeroSequence` рисует на canvas кадры `001.webp` … `174.webp` из папки
`sequence/{desktop|tablet|mobile}` в Supabase, режим `scroll`. Владелец:
«этот эффект мне очень нравится, я хочу, чтобы он был». На листе вместо этого
оказалась одна картинка с надписью — то есть макет не отражал структуру.
Проверено: все кадры по этим адресам отдаются, эффект можно показать на борде
живьём, а не описанием.

**Липкое меню нарисовано неверно и трогать его содержательно пока не нужно.**
Владелец: «мне нравится меню, как выглядит, его трогать пока не надо». На
сайте это ряд кнопок-пилюль с названием категории и **счётчиком вещей в ней**;
активная категория подсвечивается, неактивные приглушены. На листе оказались
простые текстовые ссылки без счётчиков — структура потеряна. Договорённость:
структура остаётся той же, дизайн дорабатывается позже или сейчас — решается
отдельно.

### Правки по замечаниям, 24 сентября

**Герой перерисован по факту.** Показан настоящий первый кадр
последовательности, под ним честная подпись: трек высотой в четыре экрана,
липкий canvas, 174 кадра, своя папка на каждое устройство. Владелец выбрал
вариант «один кадр с подписью», а не живую демонстрацию на борде.

При разборе выяснились две вещи, которые макет искажал:

- **Кадры почти белые.** Измерено на первом кадре: яркость низа 250 из 255,
  верха — 255. Поэтому логотип в коде тёмный (`text-zinc-800`), а не белый,
  как было нарисовано. Первый экран сайта — светлый и воздушный, что как раз
  совпадает со светлой темой, которую мы ведём в бой.
- **Пропущен слоган.** Внизу героя стоит «Arte da indossare» серым
  (`text-zinc-500`). В первой версии листа его не было вовсе.

**Липкое меню перерисовано по структуре и переведено на токены.** Владелец
сказал, что меню ему нравится и содержательно трогать его не надо, но на
борде оно было нарисовано простыми текстовыми ссылками без счётчиков — то
есть лист врал о структуре. Теперь это ряд кнопок-пилюль: название категории
плюс счётчик вещей в ней, активная залита акцентом, остальные приглушены.
Решение владельца — делать структуру и дизайн сразу, а не откладывать.

**Стрелки перелистывания стали появляться только при наведении мыши.**
Сделано через `@media (hover: hover)`, а не через ширину экрана: проверка
именно на наличие мыши. Разница существенна — планшет шириной 834 бывает и с
мышью, и без. На листе образцов первая карточка помечена «стрелки показаны
как при наведении», иначе их нельзя было бы разглядеть.

### Липкое меню собрано живой копией, 26 сентября

Владелец сравнил лист с работающим сайтом и указал на две вещи: раздел с
кнопками категорий на борде занимал не всю ширину, тогда как в оригинале
подложка идёт от края до края экрана; и попросил разобрать, как устроен объём
кнопок («при наведении или активной кнопке появляется тень, что придаёт очень
богатый объём») и как обыграть их стеклянность в духе Apple. На предложенные
варианты он ответил: **«изучи, как этот момент сделан в оригинальном
проекте»** — то есть решение должно опираться на код, а не на выбор из
отвлечённых вариантов. Затем: **«сделай полную копию нашего липкого меню… и
сделай точную копию в нашем дизайне»**.

#### Что показал разбор кода

**Подложка и содержимое — два разных слоя.** В `src/app/page.tsx` шторка это
внешний `div` с `w-full` и стеклом, внутри которого
`max-w-screen-2xl mx-auto px-4 md:px-8 lg:px-12`. Подложка тянется во всю
ширину окна, а содержимое лежит в том же контейнере, что и сетка товаров.
Поэтому первая пилюля стоит ровно над левым краем первой карточки. На борде
шторка была нарисована плавающей карточкой с полями по бокам — это просто
неверно.

**Настоящая эпловская формула стекла в проекте уже есть — ровно в одном
месте.** Подиум карточки товара, `product-card.tsx`:

```
bg-white/40  backdrop-blur-md  border border-white/50
shadow-[0_8px_32px_rgba(0,0,0,0.1), inset_0_1px_0_rgba(255,255,255,0.7)]
```

`inset 0 1px 0 rgba(255,255,255,0.7)` — это блик по верхней грани, та самая
деталь, которой объём и держится. Плюс широкая мягкая тень. Тёмная тема
прописана отдельной строкой. Формулу не надо изобретать, её надо
распространить.

**Инвентаризация стекла по проекту — шесть разных рецептов.** Подиум карточки:
фон `white/40`, блюр 12, блик есть, тень `0 8px 32px`. Липкая шторка:
`background/80`, блюр 8, ни блика, ни тени. Кнопка категории: `gray-200`,
блюра нет вовсе, тень `0 1px 2px rgba(0,0,0,.3)`. Кнопка «Show all»:
`background/50`, блюр 4. Шторки корзины и избранного: `black/40`, блюр 40.
`GlassTabs`: `black/20`, блюр 12, **дважды вложенный**. Бейдж «Продана»:
`amber-500/60`, блюр 12.

Выводы из этой таблицы:

- Блюр гуляет от 4 до 40 пикселей без системы. Но два значения — 12 и 40 —
  совпали с нашей шкалой `.glass--film` и `.glass--sheet`. Шкала выбрана не с
  потолка.
- **`saturate` не применяется нигде.** Это и есть разница между стеклом Apple
  и просто замыленным местом: под размытием цвета теряют насыщенность, и Apple
  её возвращает. Наш токен `--g-sat: 180%` в коде не представлен ни разу.
- Блик по верхней грани есть только у подиума карточки.
- **Кнопка категории вообще не стеклянная** — `bg-gray-200` непрозрачный.

#### Принятое решение и почему именно оно

Шторка остаётся стеклом, пилюли внутри стеклом не становятся; объём берётся
рельефом. Обоснование опирается на находки, а не на вкус:

1. **Стекло стоит тратить там, где под ним что-то движется.** Под шторкой
   проплывают крупные фотографии одежды — это лучшее место для стекла на всём
   сайте. Внутри пилюли не движется ничего, там фон самой шторки: второе
   стекло не покажет нового, только замутит уже размытое.
2. **Автор кода интуитивно пришёл к тому же.** Внутрь стеклянной шторки он
   поставил плотную плашку `bg-gray-200`, а не второе стекло. Решение не
   ломает замысел, а доводит начатое до конца.
3. **Что бывает иначе, видно в `glass-tabs.tsx`:** внешний `div` с
   `bg-black/20 backdrop-blur-md`, и внутри него ещё один точно такой же.
   Размытие применяется дважды, фон уходит в кашу. Это недосмотр, и живое
   доказательство, зачем нам правило «стекла в стекле не бывает».

**Решения владельца по ходу разбора.** Активная пилюля остаётся залитой
акцентом — хотя в коде она серая с янтарным текстом, владелец выбрал заливку.
Иконки профиля, избранного и корзины остаются внутри прокручиваемой ленты и
уезжают вбок вместе с категориями: владелец выбрал «оставить как есть». Это
безопасно потому, что сердце и корзина всё равно скрыты на узких экранах
(`hidden md:flex`), а их место там занимает нижняя панель `MobileFabs`.

#### Что сделано на борде

Лист «Главная» пересобран целиком и переименован в **«Главная · липкое меню
живьём»**. Он больше не картинка: внутри артборда сделан отдельный
прокручиваемый экран, потому что `position: sticky` привязывается к
прокручиваемому предку, а артборд — не окно браузера. Только так можно
показать поведение, а не нарисовать его.

Работает по-настоящему: шторка прилипает к верхнему краю, нажатие на категорию
перематывает к её блоку, активная подсвечивается по ходу прокрутки.
Скролл-спай перенесён из `sticky-nav.tsx` дословно — линия на 106 пикселях от
верха, активной становится последняя категория, чей верх её уже миновал, а
если ни одна не миновала и прокрутка меньше 100, подсвечивается первая.
Прыжок учитывает `scroll-mt-24` из кода, то есть 96 пикселей под шторку.

Повторено из кода без изменений: высота ленты 56 пикселей (`h-14`), промежуток
32 (`gap-8`), горизонтальная прокрутка со скрытой полосой и привязкой
(`overflow-x-auto no-scrollbar snap-x`), счётчик на пилюле в позиции
`-top-1 right-0`, блок иконок с `ml-auto`, полями по 24 и левой границей
`border-amber-300/30`, сердце и корзина под `hidden md:flex`, сетка секций
1 / 2 / 4, поля контейнера 16 / 32 / 48, кнопка «Показать все (N)» со счётом
`totalAvailable - 4` — поэтому у «Сумок» (4) и «Костюмов» (3) её нет вовсе, а
у «Лонгсливов» (12) она обещает 8.

Изменено против кода, осознанно и с пометкой на листе:

- Блюр шторки поднят с 8 до 12 пикселей и добавлен `saturate(180%)` — ровно
  формула подиума карточки, вместе с бликом по верхней грани.
- Объём пилюль собран из трёх слоёв вместо одного: блик по верхней грани,

  наведение — вдавленная ниша, активная — приподнятый выступ.
- Длительность наведения снижена с 500 миллисекунд до 150. В коде на наведении
  стоит `duration-500`, а на активном состоянии `duration-100`; полсекунды
  кнопка ощутимо залипает под курсором.
- На планшете лист показывает две карточки в секции, на телефоне одну. Иначе
  внутри демонстрационного экрана набирается два десятка прокруток и колесо
  мыши в нём вязнет при осмотре борда.

#### Чем проверено

Измерением, на 1440, 834 и 390, в обеих темах.

- Шторка: `position: sticky` подтверждён, при прокрутке уходит с 289 пикселей
  на 1 и держится; `backdrop-filter: blur(12px) saturate(1.8)`.
- Ширина: подложка равна ширине экрана на всех трёх устройствах.

  десктопе, 33 на планшете, 17 на телефоне, то есть поля 48 / 32 / 16 плюс

- Скролл-спай: шесть категорий из шести подсветились верно, при возврате
  наверх — первая.
- Прыжок по клику: промах ноль на всех проверенных категориях, подсвечивается

- Сетка: 4 / 2 / 1 колонки, как `sm:grid-cols-2 lg:grid-cols-4`.

плавной прокрутки на две с половиной тысячи пикселей. Оба подтвердились
исправными после правильного ожидания.

### Стекло в стекле разобрано на макете, 29 сентября

Владелец попросил показать двойное стекло наглядно и сделать компонент без
него: «убираем двойное стекло… покажи двойной вид стекла… сделай этот
компонент и покажи, как он будет выглядеть без него на дизайне». Заведён лист
**«Переключатель · стекло в стекле»**.

#### Находка оказалась шире, чем думали

`glass-tabs.tsx` рисует два вложенных `div` с одинаковым набором стеклянных
классов: строки 51 и 58 отличаются только `z-20` снаружи и `relative` внутри.
Компонент стоит в двух местах — переключатель «фото / 360°» в галерее товара
(`product-gallery.tsx:95`) и переключатель входа и регистрации в модалке
(`auth-dialog.tsx:129`).

**Но модалка устроена точно так же.** `auth-dialog.tsx`, строки 116 и 117:
стеклянный `DialogContent`, а внутри него ещё один стеклянный `div` с тем же
`bg-black/20 backdrop-blur-md`. Вместе с переключателем внутри получается
**четыре стеклянных слоя один в другом**.

#### Что это даёт в цифрах

Прозрачности складываются по формуле наложения, размытия — как корень из суммы
квадратов, а не простым сложением.

| Свойство | Задумано | Галерея, 2 слоя | Модалка, 4 слоя |
| --- | --- | --- | --- |
| Затемнение фона | 20 % | 36 % | 59 % |
| Размытие | 12 px | ≈ 17 px | ≈ 24 px |
| Рамок по краю | 1 | 2 | 4 |
| Теней | 1 | 2 | 4 |
| Отступ переключателя | 4 px | 8 px | 8 px |

Под четырьмя слоями фотография перестаёт быть фотографией — остаётся ровное
серое пятно. Стекло работает наоборот: сквозь него должно быть видно, что
там, просто мягко. Плюс удвоенная рамка на расстоянии пикселя читается как
сбитая печать.

#### Починка оказалась не просто «убрать лишний слой»

Первая версия макета повторила разбираемый дефект: в «починенной» модалке
переключатель остался стеклом внутри стеклянной модалки. Исправлено, и заодно
сформулировано правило, которое из этого следует:

**Отделка зависит от того, что под элементом.** Модалка сама по себе стекло —
она плавает над страницей, это её законное место. А раз она стекло, то
переключатель внутри неё стеклом быть уже не может: он становится **нишей**,
ровно как пилюли категорий внутри липкой шторки. Над фотографией — стекло,
внутри стекла — углубление. Правило одно, решений два.

Поэтому на листе «будет» для галереи — одно стекло, а для модалки — одно
стекло плюс ниша.

#### Чем проверено

Вложенность измерена на макете: 2 слоя у нынешней галереи, 1 у починенной,
4 у нынешней модалки, 1 стекло плюс 1 ниша у починенной. Параметры каждого
слоя совпадают с кодом: `blur(12px)`, `rgba(0, 0, 0, 0.2)`. Проверено на 1440,
834 и 390 в обеих темах, вылет за край ноль. Таблица из четырёх колонок не
помещалась в 390 — ей нужно 392 пикселя — и убрана в собственную
горизонтальную прокрутку, чтобы не толкать лист вбок.

Зрительная проверка сделана, хотя сперва я решил иначе. Снимок экрана из
безголового браузера записывался в корень репозитория, а не в каталог
Playwright, где я его искал, — и я ошибочно заключил, что снимки не работают.
На самом деле работают, и разница на снимке читается: у нынешнего
переключателя кромка заметно тяжелее, а ткань под ним теряется; сквозь
починенный снимок проходит.

#### Решение по переносу в код ещё не принято

Починка — удаление, а не добавление: внешние обёртки нужны только чтобы
принять `className`, отступ и слой по оси Z, вся работа идёт во внутренних,
там лежит `ref` для белой плашки. Достаточно снять стеклянные классы с
внешних. Затрагивает `glass-tabs.tsx` и `auth-dialog.tsx`. В задачи для
переноса в код пока не занесено.

### Рельеф заведён в дизайн-системе, 29 сентября

Владелец согласился с правками и поручил провести их **по всему дизайну**, а
не только на разборном листе: «внеси эти правки в главный дизайн… чтобы всё
соответствовало и было в одном стиле». Код при этом не трогаем до конца
дизайна — владелец проверит целиком, и только тогда начнётся перенос.

#### Сплошная проверка борда

Проведён поиск стекла в стекле по всем 35 макетам — не по именам классов, а по
вычисленному `backdrop-filter`: элемент считается нарушителем, если у него
есть стеклянный предок внутри того же артборда. Так метод ловит и случаи,
собранные из разных классов.

Результат оказался лучше ожидаемого: **единственное настоящее нарушение** — на
листе «Товар · продана и забронирована» кнопка «в избранное» со стеклом стоит
внутри стеклянной плашки «Продана» (и её двойник в плашке «Бронь до»).
Остальные срабатывания — образцы «как сейчас» на разборном листе, они
показывают дефект намеренно.

#### Главная находка: правило было, а примитива не было

В дизайн-системе правило сформулировано давно — «стекло в стекле запрещено,
вложенный элемент либо плотный, либо ниша». Но **самой ниши в системе не
существовало.** Ни класса, ни токенов, ни показа. Поэтому каждый экран
изобретал её заново, и к сегодняшнему дню их было три разных:

- пилюли липкой шторки при наведении — `inset 0 1px 2px rgba(69,42,8,.10)`;
- переключатель внутри модалки — `inset 0 1px 3px rgba(0,0,0,.38)`;
- поля ввода — своё описание словами, без общей формулы.

Это и был источник разнобоя, на который указал владелец. Правило без примитива
не работает: оно обязывает, но не даёт чем.

#### Что заведено

**Пять новых токенов рельефа**, в обеих темах: `--well-deep`, `--well-lip`,
`--lift-edge`, `--lift-near`, `--lift-far`.

**Два примитива.** Логика общая и держится на одном: свет падает сверху.

```
.niche  { background: var(--well); border: 1px solid var(--well-line);
          box-shadow: inset 0 1px 3px var(--well-deep),
                      inset 0 -1px 0 var(--well-lip); }

.raised { box-shadow: inset 0 1px 0 var(--lift-edge),
                      0 1px 2px var(--lift-near),
                      0 7px 18px -7px var(--lift-far); }
```

Ниша вдавлена, поэтому тень лежит на её верхней кромке, а светлая грань — на
нижней. Выступ ровно наоборот: блик по верхней грани, близкая тень-контакт и
широкая тень-отрыв.

**Раздел «Рельеф» на листе дизайн-системы** — три отделки рядом, ниша, выступ
и стекло, с подписью, где какая применяется, и с формулой.

**Новая карточка в правилах:** «Над фотографией стекло, внутри стекла ниша».
Формулировка важна тем, что переносит решение с элемента на его окружение:
отделка зависит не от того, что это за элемент, а от того, что под ним. Один и
тот же переключатель над снимком — стекло, а внутри стеклянной модалки —
углубление.

**Сведены к одной формуле** все самодельные ниши: переключатель в модалке,
наведение и активное состояние пилюль категорий, и починенное сердце в плашке
«Продана».

#### Чем проверено

Повторный поиск стекла в стекле: вне разборного листа — чисто. Сердце в плашке
«Продана» — `backdrop-filter: none`, фон и тень совпадают с `.niche` до
значения. Три разных места, где применяется ниша, дают **побайтово одинаковые**
вычисленные тень и фон. Обе темы дают свои значения и не наследуют чужих.
Вылет за край — ноль по всем 35 макетам на 1440, 834 и 390.

### Пометки убраны с макетов, 29 сентября

Найдено при сплошной проверке и **исправлено как собственный дефект прошлых
шагов.** Панель пометок `.ca-flags` стояла абсолютно в правом верхнем углу
артборда, и на трёх листах — «Оформление · форма», «Шторка корзины»,
«Карточка товара · четыре состояния» — она **накрывала сам макет**: названия
вещей, размеры, заголовок сводки. Перекрытие доходило до 189 пикселей по
горизонтали и 61 по вертикали.

Почему не поймали раньше: все прежние проверки мерили **вылет за край сцены**.
Панель за край не выходила — она лежала поверх содержимого внутри сцены, и
такой замер её пропускал. Добавлена вторая проверка, на **взаимное наложение
читаемых блоков**; именно она и нашла все три случая.

Решение: пометки всегда идут в потоке над макетом и на всю ширину, одинаково
на всех устройствах. Это не новое изобретение — ровно так система уже вела
себя на узких экранах, где `.ca-flags` становилась обычным блоком. Теперь то
же поведение распространено на все ширины, и заодно совпало с тем, как
устроен лист «Переключатель · стекло в стекле».

Побочно нашлась та же ошибка на новом листе: три плашки `.su-flag` были
поставлены напрямую, без контейнера `.ca-flags`, а сама `.su-flag` по
умолчанию абсолютная — все три легли друг на друга и поверх демонстраций.

Проверено на 1440, 834 и 390: наложений панели на макет нет ни на одном из
35 листов, вылетов за край нет.

### Шаг 4 — профиль. Разбор кода и задание для отдельного окна

Разбор сделан 29 сентября в окне, которое вело шаги 1–3. Сам шаг решено
выносить в **отдельное окно**: восемь файлов, семь подпунктов и несколько
решений, меняющих структуру. Всё нужное лежит не в переписке — решения здесь,
а примитивы `.niche` и `.raised` в артефакте.

#### Что представляет собой профиль в коде

`src/app/profile/page.tsx` — серверный компонент, 58 строк. Проверяет сессию,
иначе `redirect('/')`. Одним запросом тянет пользователя вместе с `favorites`,
`cartItems` и `orders` (с позициями и товарами, сортировка по убыванию даты).
Рендерит логотип-ссылку, `ProfileHeader` и `ProfileTabs`.

Компоненты в `src/components/shared/profile/`: `profile-header` (31),
`profile-tabs` (88), `animated-profile-list` (61), `profile-item-card` (31),
`order-card` (126), `empty-tab-state` (21), `tab-trigger-item` (28).

#### Решения владельца, принятые при разборе

1. **Вкладка «RESERVATIONS» переименовывается в «Корзину».** В коде она
   называется «Брони», а показывает корзину: `useShopStore(state => state.cart)`.
   Обещание ложное — положить вещь в корзину её не бронирует. Бронь в этом
   магазине возникает только при оформлении, когда заказ уходит в `PENDING` и
   у товара проставляется `reservedUntil`. Для магазина единичных вещей такое
   обещание опасно, поэтому вкладка называется тем, чем является.
2. **Кнопка «Оформить заказ» убирается с вкладки избранного.** Владелец:
   «ей в избранном просто избранное. Если человек захочет его заказать, он
   добавит в корзину и придёт в неё». Сейчас `animated-profile-list.tsx`
   рисует `CheckoutButton` независимо от типа списка, поэтому под избранным
   висит кнопка, ведущая на `/checkout`, где лежит совсем другой набор вещей.
3. **«Ожидает оплаты» дорабатывается.** Статус `PENDING` показывается как
   `AWAITING PAYMENT`, но заплатить рядом нечем. Человек видит зависший заказ
   и ничего не может с ним сделать, пока бронь на товар тикает.

#### Подпункты

- **4.1 Шапка профиля.** Аватар, имя, почта, выход. Стеклянная плашка на всю
  ширину, `bg-white/5 backdrop-blur-xl border border-white/10 rounded-[32px]`.
- **4.2 Полоса вкладок.** Три вкладки со счётчиками. Прямое место для рельефа:
  `TabsList` уже углубление (`bg-white/5 border`), активная вкладка — белая
  плашка (`data-[state=active]:bg-white`). Это буквально `.niche` и `.raised`.
- **4.3 Вкладка «Коллекция»** — избранное, сетка в две колонки, переиспользует
  `SheetItemCard`, уже нарисованный на листах шторок.
- **4.4 Вкладка «Корзина»** — бывшие «Брони», переименование по решению 1.
- **4.5 Карточка заказа** — самый крупный кусок, см. находки ниже.
- **4.6 Пустые состояния** — три штуки, сейчас иконка плюс строка, без действия.
- **4.7 Сквозное** — русский язык, формат дат и денег.

#### Находки, по которым решения ещё нет

- **Итог заказа пересчитывается, хотя снимок есть.** `order-card.tsx` складывает
  `priceAtOrder` по позициям, а в базе лежит `Order.totalAmount` — «снимок суммы
  на момент заказа», как написано в самой схеме. Сегодня числа совпадут:
  у `OrderItem` нет поля количества, товар единичный. Но как только появится
  доставка или скидка, карточка начнёт показывать не то, что человек заплатил.
- **Адрес доставки не показан вообще.** В `Order` лежат `shippingCountry`,
  `shippingCity`, `shippingPostalCode`, `shippingStreet`, `shippingState` — в
  профиле не выведено ни одно поле. А это как раз то, ради чего чаще всего
  возвращаются в историю: «куда я это заказал».
- **Номер заказа — обрезанный UUID:** `order.id.split('-')[0].toUpperCase()`.
  Упирается в задачу 10, отложенную ранее.
- **`text-grey/40`** на строке почты в `profile-header.tsx`: в Tailwind цвет
  называется `gray`, своего `grey` в проекте нет. Класс не делает ничего.
- **Всё по-английски**, включая `Intl.DateTimeFormat('en-US')` — даты выходят
  как «14 Mar 2026». Английские строки: MY COLLECTION, RESERVATIONS, ORDER
  HISTORY, Your collection is empty, No active reservations, No previous
  orders, Order Date, ID, TOTAL, и все подписи статусов — AWAITING PAYMENT,
  PREPARING, SHIPPED, CANCELLED.
- **Вкладки на телефоне идут столбиком:** `grid-cols-1 md:grid-cols-3`, каждая
  строка высотой `py-4`. Полоса превращается в список из трёх строк.
- **Фотографии в заказе во всю ширину карточки**, по одной на позицию. Заказ
  из трёх вещей даёт очень длинную карточку, а заказы стоят в две колонки —
  соседние разъезжаются по высоте.

#### Как делить работу между окнами

Предложено два захода, а не один:

- **Окно А — каркас и списки:** 4.1, 4.2, 4.3, 4.4, 4.6. Здесь же рельеф идёт
  в дело на полосе вкладок, а списки переиспользуют уже нарисованную карточку
  из шторок, так что заход выходит компактным.
- **Окно Б — карточка заказа:** 4.5. Там больше всего нерешённого — адрес,

### Шаг 4 закрыт 29 сентября: профиль целиком

Нарисованы три листа — «Профиль · избранное», «Профиль · корзина и пустые

1. **Первая вкладка называется «Избранное», а не «Моя коллекция».** Тот же

3. **Кнопка выхода остаётся красной.** Предлагалось сделать её нейтральной по

4. **Над кнопкой «Оформить заказ» появился итог.** В шторке корзины сумма

   показывает ровно тот же список.

#### Что нарисовано

**Шапка профиля (4.1)** — единственное стекло на экране. Так уже в коде
(`bg-white/5 backdrop-blur-xl`), и так остаётся: шести стеклянным карточкам
списка взяться неоткуда, правило «не больше трёх-четырёх стёкол на экране» не
резиновое. Всё остальное берёт объём рельефом.

**Полоса вкладок (4.2)** — второе место в приложении, где рельеф пошёл в дело
(первое — пилюли липкого меню главной). Ничего не придумано заново: в коде
`TabsList` уже углубление, а активная вкладка уже плашка. Белая плашка
заменена янтарным выступом и добавлено освещение. Счётчик вынесен из подписи
в отдельную пилюлю: по-русски подпись длиннее, а «(4)» заголовочным шрифтом
внутри строки читается как часть названия. На листе есть отдельный разбор трёх
состояний — покой, наведение, активная.

**Списки (4.3 и 4.4)** — те же `sheet-item-card`, что в шторках, ни одной
новой формы. В избранном показаны все четыре случая разом: доступная вещь с
кнопкой «В корзину», проданная и забронированная с бейджем вместо кнопки.

**Итог и кнопка (4.4)** — одной полосой-нишей, а не кнопкой во всю ширину. В
коде `CheckoutButton` завёрнут в `Link className="block w-full"` и
растягивается на все 1024 пикселя колонки. На телефоне полоса складывается, и
кнопка снова во всю ширину.

**Пустые состояния (4.6)** — та же ниша, что под вкладками, только кромка
пунктиром: место под содержимое есть, самого содержимого нет. Тексты написаны
под конкретную вкладку, а не один на троих. В каждом появилась кнопка «В
каталог» — предложение, ждёт решения владельца.

#### Найдено в коде по ходу работы

- **Аватарка-заглушка не показывается никогда — это баг, а не стиль.**
  `profile-header.tsx` передаёт `isLoading={!user.image}`, а `user-avatar.tsx`
  при `isLoading` рисует `Skeleton`. У покупателя, зарегистрированного почтой
  без OAuth, `image` пуст всегда, поэтому серый пульсирующий круг остаётся
  навсегда, а ветка с `UserIcon` недостижима. На макете нарисовано то, что
  должно быть видно.
- **`text-grey/40` на строке почты не делает ничего.** В Tailwind цвет
  называется `gray`, своего `grey` в проекте нет, поэтому почта сейчас того же
  цвета и веса, что имя над ней.
- **Заголовочный шрифт не содержит кириллицы.** Проверено по самому файлу
  `rush_zone.otf` (в коде `font-jane`): латинские глифы в нём есть, русских
  нет ни одного. Пока интерфейс был английским, это не проявлялось; после
  перевода каждый русский заголовок молча падает на запасной `Arial Narrow`.
  Это **касается всей задачи 12, а не только профиля** — на листах шагов 1–3
  ровно то же самое, просто никто этого не называл. Решение нужно одно на весь
  перевод: либо кириллический шрифт под пару к RushZone, либо осознанный
  выбор, что по-русски заголовки набираются другим шрифтом. Вынесено плашкой
  на лист «Профиль · избранное» и отдельным абзацем в раздел «Шрифт»
  дизайн-системы.

#### Починено на самом борде

Правило `.su-flag b` било по **всем** `<b>` внутри плашки-пометки, и от этого
ломались две вещи разом. Выделение в тексте превращалось в ещё одну
строку-заголовок — красную, заглавными, с отбивкой. А подпись «Подтверждено»
на зелёных плашках всё равно выходила красной: у `.su-flag--ok b` и
`.su-flag b` одинаковая специфичность, и побеждало то, что ниже по файлу.
Заменено на дочерний селектор с `:first-child`. Починка задела четыре старые
плашки на листах шагов 1–3, они тоже стали выглядеть как задумано.

#### Карточка заказа (4.5): решения владельца

1. **Крупные фотографии остаются.** Предлагалось свести позиции заказа к тем
   же строкам, что в избранном и корзине, — высота стала бы предсказуемой, а
   колонки перестали бы разъезжаться. Владелец выбрал сохранить витрину:
   история заказов показывает купленные вещи, а не бухгалтерскую ведомость.
   Следствие принято осознанно и нарисовано на макете специально — второй
   заказ показан из двух вещей, чтобы было видно, как под короткой соседкой
   образуется провал. Единственное смягчение: сетке добавлен
   `align-items: start`, чтобы короткая карточка хотя бы не растягивалась
   пустотой внутрь себя.
2. **Номер заказа нарисован в желаемом виде — `JA-260929-041`:** префикс,
   дата задом наперёд, порядковый номер за день. Макет становится техзаданием
   для отложенной задачи 10. Порядковый счётчик потребует нового поля в базе и
   транзакции на выдачу; если заводить его не захочется, тот же вид без
   счётчика даёт `JA-260929-4F2A` — дата плюс четыре символа существующего
   UUID.
3. **На зависшем заказе есть обратный отсчёт и кнопка «Оплатить».**
4. **Адрес доставки отложен.** Владелец решил вернуться к нему позже, вместе с
   доработкой плашки пользователя. На макете место под него размечено —
   строка между составом и итогом, — и помечено плашкой «Отложено», чтобы
   пункт не потерялся.

#### Главная находка: доплатить зависший заказ можно уже сегодня

Механизм существует в коде, до него просто нельзя добраться из профиля.
`collectPendingOrders` в `src/actions/checkout.ts` при заходе на `/checkout`
находит живую сессию Stripe **с тем же составом и той же суммой** и
возвращает её ссылку вместо создания новой. А корзина при переходе заказа в
`PENDING` не очищается — это происходит только в `fulfillOrder` после оплаты.
Значит кнопке «Оплатить» на карточке зависшего заказа **не нужен новый
бэкенд**: она ведёт на `/checkout`, и человек попадает на ту же страницу
оплаты, что бросил.

Срок для обратного отсчёта тоже уже лежит в базе: `Order.expiresAt`. В коде
`DB_RESERVATION_MINUTES = 40`, а сессия Stripe живёт 32 минуты
(`STRIPE_SESSION_MINUTES`), поэтому таймер честен и не обещает больше, чем
есть.

#### Находки по карточке заказа, требующие работы в коде

- **Итог пересчитывается, хотя снимок уже есть.** Карточка складывает
  `priceAtOrder` по позициям, а рядом лежит `Order.totalAmount` — «снимок
  суммы на момент заказа», как написано в самой схеме. Сегодня числа
  совпадут: у `OrderItem` нет количества. Разойдутся они в тот день, когда
  появится доставка или скидка, и карточка начнёт показывать не то, что
  человек заплатил.
- **Причины отмены в базе нет.** Заказ отменяется тремя разными путями:
  истекла бронь и его погасил крон, Stripe отказал в платеже, человек ушёл со
  страницы оплаты. Все три выглядят одинаково — «Отменён». Между «не успели» и
  «карта не прошла» разница большая, а выяснить её человеку негде. Решения
  пока нет; нужно либо поле с причиной, либо хотя бы различение истёкшей
  брони, которое выводится из `expiresAt`.
- **Плашка с названием на фотографии всегда тёмная** — в коде `bg-black/40`
  с белым текстом независимо от темы. На макете приведена к общей формуле
  стекла и переключается вместе с темой.
- **Даты по-английски.** `Intl.DateTimeFormat('en-US')` даёт «14 Mar 2026».
  Это единственное место в профиле, где даты вообще выводятся. На макете —
  «29 сентября 2026», без канцелярского «г.» на конце.

#### Статусы заказа по-русски

`PENDING` → «Ожидает оплаты», `PAID` → «Готовим к отправке», `SHIPPED` →
«Отправлен», `CANCELLED` → «Отменён». У каждого своя иконка, поэтому статус
читается формой, а не только цветом. Синего в палитре нет, и заводить его
ради одного статуса не стали: «Готовим к отправке» — зелёный контуром,
«Отправлен» — тот же зелёный заливкой. Одна семантика, две ступени, видна
последовательность.

### Отложено до конца дизайна: сохранить борд вне артефакта

Владелец спросил, как сохранить дизайн, чтобы он хранился не только в
артефакте, и можно ли открыть его в Figma. Решено сделать **когда дизайн
будет закончен**, сейчас не трогаем.

**Figma отпадает.** Импорта HTML у неё нет, а плагины вроде html.to.design
разваливают ровно то, чем борд ценен: `backdrop-filter`, контейнерные запросы,
живое липкое меню, переключатель тем. К тому же борд — не макет, который надо
перерисовывать, а настоящий CSS с настоящими токенами: он пойдёт в код
напрямую, и Figma была бы лишним переводом туда-обратно.

**Что делаем вместо этого:** кладём файл борда в репозиторий, например
`docs/design/board.html`. Одна самодостаточная страница около 1,9 МБ,
фотографии внутри, открывается двойным кликом, версионируется вместе с кодом
и переживает чистку скретчпада — а она за время работы случалась дважды.

Оговорка, из-за которой это и откладывается: файл крупный, и git при каждом
сохранении хранит его целиком заново. Класть туда нужно **готовый дизайн**, а
не каждую правку, иначе репозиторий распухнет.

**Дополнительно, по желанию:** выгрузка всех листов в PNG, по файлу на лист —
если понадобится перетащить в Figma, показать кому-то или вложить в
презентацию.

### Шаг 4, дополнение: плашка пользователя и данные для доставки

Задание составлено 8 октября. Владелец вспомнил о недоделанном: в плашке
профиля есть аватар, имя, почта и выход — и он хочет добавить туда
разворачивающийся блок с данными для доставки. **Рисуется в отдельном окне.**

Это же дополнение закрывает то, что шаг 4 отложил: адрес доставки на карточке
заказа был отложен «вместе с доработкой плашки пользователя».

#### Находка, с которой всё начинается: поля есть, но не заполняются никогда

В `User` под доставку лежит восемь полей: `phone`, `firstName`, `lastName`,
`country`, `city`, `postalCode`, `street`, `state`. Ровно их же собирает форма
оформления — все обязательные, кроме `state`.

**Но `prisma.user.update` не встречается в коде нигде** — проверено по всему
`src/`, кроме сгенерированных типов Prisma. Данные покупателя при оформлении
уходят только в `Order` как снимок (`src/actions/checkout.ts`, строки 227–234).
В `User` — ни строчки.

При этом `src/app/checkout/page.tsx` честно **читает** эти восемь полей, чтобы
подставить в форму, и всегда получает `null`, который превращается в пустые
строки. **Подстановка в форму — мёртвый код.** Человек каждую покупку заново
набирает имя, фамилию, телефон, страну, город, индекс и улицу.

#### Две сущности, которые нельзя смешивать

Владелец сформулировал разделение, и оно снимает ловушку, в которую я чуть не
завёл. Предлагалось сохранять данные формы в профиль при каждом оформлении —
но тогда заказ в подарок другу молча перезаписал бы собственный адрес
покупателя, и следующая покупка для себя уехала бы не туда.

| | где лежит | что означает |
| --- | --- | --- |
| **Мои данные** | `User`, 8 полей | куда поедет **следующий** заказ по умолчанию |
| **Данные заказа** | `Order`, свой снимок | куда поехал **этот** заказ |

Снимок в `Order` уже делается правильно. Не хватает только того, чтобы `User`
когда-нибудь заполнялся.

#### Решение владельца: галочка на странице оформления

Три случая, все названы владельцем дословно:

1. **Данных нет вообще.** Галочка **включена автоматически и показана
   активной**, рядом примечание, что данные будут сохранены в профиль. Человек
   ничего не делает и получает заполненный профиль. Рисковать нечем — терять
   нечего.
2. **Данные в профиле есть** (заполнил заранее либо покупка не первая). Форма
   выдаётся **уже заполненной** его данными, а галочка **снята**. Профиль сам
   собой не меняется.
3. **Подарок или переезд.** Если заказ другому человеку — просто меняет данные
   в форме, галочка остаётся снятой, свой профиль цел. Если переехал или
   изменились постоянные данные — меняет их там же и **ставит галочку сам**,
   тогда профиль перезаписывается.

Смысл: автоматика помогает там, где риска нет, и молчит там, где он есть.

#### Устройство плашки

**В покое плашка закрыта.** Видно только то, что видно сейчас: аватар, имя,
адрес почты, кнопка «Выйти» — и один скромный блок-переключатель. Владелец
отдельно просил, чтобы он **не бросался в глаза**: неконтрастная подпись,
маленькая стрелка-уголок, которая переворачивается вверх при раскрытии.

**Подпись зависит от того, есть ли данные.**
- Данных нет — подпись зовёт заполнить («Заполнить данные для доставки») и
  получает акцент: это единственный случай, когда блок должен привлекать
  внимание.
- Данные есть — спокойная подпись («Личные данные»), без акцента.

**Внутри раскрытой плашки — два раздела, между которыми человек переключается**
(именно переключается, а не два независимых аккордеона один под другим):
- **Личные данные** — имя, фамилия, телефон, почта.
- **Адрес доставки** — страна, город, индекс, улица, регион.

#### Что рисовать: три состояния

1. **Покой** — плашка закрыта, виден только блок-переключатель.
2. **Раскрыто, выбран раздел «Личные данные».**
3. **Раскрыто, выбран раздел «Адрес доставки».**

Плюс отдельно показать **случай без данных** — подпись с акцентом и пустые
разделы. У всех нынешних пользователей там пусто, и это надо не прятать, а
обращать в приглашение.

#### Отделка

Шапка профиля — **единственное стекло на экране**, это решено на шаге 4 и
остаётся. Значит всё внутри неё берёт объём рельефом: разделы в покое — ниши,
выбранный раздел — выступ, ровно как полоса вкладок самого профиля.
Примитивы `.niche` и `.raised` описаны в разделе «Рельеф» дизайн-системы.

#### Нерешённое, вынести плашкой на макет

**Два имени.** В базе есть `name` от авторизации (сейчас показан в шапке) и
